# docs-business — 业务流程（业务全景 + 需求）

## 定位与管辖文档

- 管辖 `docs/L1/BUSINESS.md`（业务流程），一份文档同时承载业务侧与需求侧：业务定位与目标、业务全景（参与方与角色、业务主线、业务模式、业务对象与系统流转、系统边界与主责、业务关系图、角色关系图）、产品能力（图例、能力架构图、能力清单）、用户故事（清单、详情、业务验收标准）、用户旅程（总旅程、单故事交互）。
- 目标文档骨架的唯一来源是 [assets/TEMPLATE.md](assets/TEMPLATE.md)。生成或更新前必须先读取该文件，并严格沿用其中的章节编号、标题层级和结构；本 skill 不另存或扩写目标文档骨架。
- 本 skill 只提供执行方法与内容规范，不承载项目具体取值；实例文档只写项目业务与需求事实。
- 业务对象字段、状态机、约束及能力到领域操作 Action 的映射归 `docs-domain` skill，本文档只写跨系统业务流向。
- 应用与技术边界归 `docs-application-architecture` skill，跨系统接口契约归 `docs-outbound` skill，本文档只写业务级边界、流向与主责。
- 业务验收标准由本 skill 定义；技术验收、测试用例与 `docs/test/` 测试资产归 `test-ops` skill。
- 同一信息只维护一次，其他位置只引用。L1 可引用 L2、L3、L4，不链接 L0 路径；同级文档可协作引用。
- 图必须以 D2、Mermaid 或 ASCII 代码块写入 Markdown；容器式分层图使用 D2 并遵循 `c4-container-diagram` skill，其余图使用 Mermaid，无法渲染时退化为 ASCII。图旁只标图名，不复制绘制方法。
- 图型分工：业务主线图、系统外故事外部流程用 Mermaid flowchart；角色关系图用 Mermaid classDiagram；用户旅程与单故事交互动用 Mermaid sequenceDiagram；业务关系图、能力图例与产品能力架构图用 D2。D2 图保留图名、视角、用途和边界等自描述信息。
- 产品能力清单与能力状态只在本 skill 维护。能力图不列不存在的功能，不记录已砍掉能力或「无 Action」，历史决策归 Git。
- 能力状态默认用实线表示已实现（含本迭代）、虚线表示待规划，必要时可用点线表示中间态；优先级可选核心、支撑、边缘，并与架构图热力色对应，未使用则省略；入口层不参与状态编码。
- 能力与领域操作 Action 是 1:N 映射，Action 详情归 `docs-domain` skill。能力域取业务域；被两个及以上垂直能力共用的能力归共享业务服务层，单一业务能力归垂直层，开箱自带且无管理界面的能力标为系统内置。
- 垂直能力之间不互相依赖，只依赖共享业务服务层；横向能力与系统内置能力尽量解耦。
- 角色覆盖产品全部用户角色（含系统内与系统外）；业务关系图（系统边界与业务流向视角）与角色关系图（角色间协作视角）分工明确、不重复。
- 用户故事是需求最小单元；故事只写用户意图、结果和边界，不写实现细节；单个故事自包含，允许为读者理解而适度重复。
- 文档不设承载文档索引章或相关文档聚合链接章，内容条目不使用顺序编号（US-N / 场景 N / AC-N 等），Mermaid autonumber 不受此限制。

## 读取

- `docs-align` skill 是跨文档编排器；本 skill 属 L1，生成前先读取项目宪法作为 L0 基线。
- 生成前读取 L2 的领域模型（`docs-domain`）的业务对象与领域操作、应用架构（`docs-application-architecture`）、集成契约（`docs-outbound`）与深潜（`docs-deep-dives`）的关联产物。
- 项目文档按 L0 → L1 → L2 → L3 → L4 → common 的顺序生成；生成下层文档前先读上层产物。
- 已有 BUSINESS.md 时先提取仍有效的业务事实、角色关系、能力状态、故事与旅程，不沿用已失效的结构或描述。

## 生成流程

以下情况触发生成：新建、编辑或重建 BUSINESS.md；关联产物变化需要联动更新；用户明确要求生成。

1. 先读取 [assets/TEMPLATE.md](assets/TEMPLATE.md)，以模板顺序和标题层级作为写作基准。
2. 自主读取项目宪法、需求来源、关联文档和现有 BUSINESS.md，提取可验证事实，不臆造缺失信息。
3. 先写业务侧（业务定位、业务全景、产品能力），再写需求侧（角色、用户故事、用户旅程）；需求侧必须与业务侧的能力、参与方对齐。
4. 已有文档仅复用仍有效的信息，按模板重新组织；模板中用不到的位置保留标题并留空。
5. 按模板写入内容，删除模板说明、占位符和填充提示；正文不写构建元信息、写法约束、治理套话或 SSOT 标签，不使用加粗与 emoji，frontmatter 不增加模板未定义的内容。
6. 使用规定格式写入图、表与文字，并让同一事实的图、表和正文保持一致。
7. 系统内故事使用 Connextra 三段式、Given-When-Then 验收标准和关联信息；系统外故事使用 Connextra、外部流程和不参与系统旅程的关联说明，不写验收标准或 Action。
8. 用户旅程与单故事交互必须满足时序图约束：使用用户、UI、系统后端三个参与者；每个用户触点形成「用户 → UI → 系统 → UI → 用户」完整闭环；系统泳道不包含 UI。总旅程每阶段只保留 1 至 3 个关键触点，阶段不超过 9 个，推荐不超过 7 个，超出时按子域拆分。
9. 单故事时序图按需表达用户操作、UI 状态、UI 到后端调用、后端黑盒处理、后端返回、UI 反馈、成功或失败分支及循环；「涉及 UI」写页面或弹窗名称与入口路径，存在 `.pen` 原型时附路径，不另建页面清单。
10. L1 时序图只描述用户、UI 与系统后端协作，不展开云函数、AI 服务、数据库、具体第三方或小程序等 L2、L3 术语。
11. 仅当代码与文档无法推出事实时询问用户：能力状态、能力域归属、角色划分、故事优先级或业务定性有歧义时确认。
12. 按完成判定逐项校验，并执行联动同步。

## 更新流程

1. 先读取 [assets/TEMPLATE.md](assets/TEMPLATE.md)，再读取现有 BUSINESS.md、项目宪法、需求来源及全部关联产物。
2. 对照模板逐项检查章节、表格和图示，保留仍有效的项目事实，删除下线能力、过期描述和重复内容。
3. 业务事实变化时同步更新相关图、表和正文；能力增删、状态变化与 Action 变化必须双向一致。
4. 角色或故事增删时，同步更新参与方与角色表、角色关系图、故事清单、故事详情和用户旅程；系统外故事不补系统内旅程或系统内时序图。
5. 增删或迁移内容后删净旧表述并保持编号连续，不保留迁移占位正文；模板要求但当前无内容的固定位置保留标题并留空。
6. 更新涉及能力的领域操作、应用边界、跨系统契约或测试来源时，按联动规则同步处理。
7. 按完成判定校验后交付，不自动 commit 或 push。

## 联动

- `docs-domain` skill：同步领域操作 Action 与业务对象；能力增删、状态变化和 Action 变化必须双向一致；故事关联的 Action 详情以其为准。
- `docs-application-architecture` skill：同步能力与模块的关联、应用边界和技术边界。
- `docs-outbound` skill：业务对象跨系统流向与外部单据必须和接口契约一致。
- `docs-deep-dives` skill：高复杂度能力可下沉详情，本文档保留业务层摘要。
- `docs-technology-architecture` skill：需要解释系统后端技术栈时读取其技术架构。
- `docs-data-architecture` skill：需要展开后端数据存储时读取其数据架构。
- 标为待规划的能力不得在 `docs-domain`、`docs-inbound`、`docs-application-architecture`、`docs-structure` 或 openapi 中建模或留占位；这些文档新增 Action 时也必须回写能力状态。
- `test-ops` skill：业务能力与用户故事是测试场景来源；新增或调整时同步测试场景；技术验收、测试用例与测试资产归 `test-ops` skill。
- `docs-align` skill：负责跨文档编排、漂移检测、初始化和旧文档迁移，本 skill 只报告并处理本文档范围内的一致性问题。

## 完成判定

以下全部通过才算完成：

- 实例文档与 [assets/TEMPLATE.md](assets/TEMPLATE.md) 的章节编号、标题层级和固定结构一致，且没有模板未定义的内容。
- 产品能力架构图的业务能力节点与能力清单中的业务能力行一一对应；共享业务服务层节点与系统内置或横向能力行按类型分别对应；能力图例独立存在，架构图内没有重复图例，入口层不参与状态编码。
- 能力清单的 Action 映射可追溯到 `docs-domain`；可选列只在有真实信息时出现，优先级与图示一致。
- 参与方与角色表覆盖产品全部用户角色，标明系统内与系统外；业务关系图与角色关系图分工清晰，不重复绘制同一关系。
- 业务主线图与阶段表一一对应，并与单角色旅程分工清晰；业务对象可追溯到 `docs-domain`，业务关系图与 `docs-application-architecture` 的系统边界不冲突。
- 横向、垂直与系统内置能力识别正确，依赖方向符合业务解耦约束。
- 故事清单中的每个故事在故事详情中有且仅有一节，角色分组一致，无遗漏或重复。
- 每个系统内故事在单故事交互中有对应时序图；系统外故事在自身详情中有外部流程图，在单故事交互中只作引用。
- 每个系统内角色都有总旅程图，系统外角色不生成系统旅程图。
- 每个系统内故事都有使用 Given、When、Then 英文术语引导的验收标准；系统外故事没有验收标准。
- 所有用户旅程和单故事时序图都满足三角色、完整链路和系统泳道不含 UI 的约束，L1 未展开 L2、L3 术语。
- 系统内故事与能力、`docs-domain` Action 一一对应；系统外故事明确标注驱动或支撑的系统内环节且无 Action。
- 内容条目无顺序编号，文档无承载文档索引章或相关文档聚合链接章。
- 产出文档无「固定元信息」「固定画法」字样，无 SSOT 字样，无加粗与 emoji，无未替换的模板说明或占位符。

## 边界

只生成与更新 `docs/L1/BUSINESS.md`，不生成其他层文档、业务代码或 Git 提交；其他文档由对应 skill 负责，跨文档编排、文档初始化、漂移检测和旧布局迁移由 `docs-align` skill 负责。
