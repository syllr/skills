# docs-align — 文档编排器

定位：文档体系的总编排器（根 AGENTS.md §2.1 差异主动修复）。把「对齐 / 漂移 / 初始化 / 旧文档处置」拆到各层，逐层调用对应 `docs-*` skill 执行——每个 skill 各自管一份文档的读取 / 生成 / 更新 / 校验（管辖关系见根 AGENTS.md「文档操作 Skill 路由」）。本 skill 不实现单份文档的生成规则，只决定调哪些 skill、按什么顺序，并做跨文档一致性核对、漂移清单、当前预期文档清单与旧文档处置。

前置：项目已安装 `docs-*` skill；未安装时先由 project-scaffold 安装。

## 2. 扫描检测（诊断流程：盘点 → 路由自适应 → 机检 → 语义核对 → 落清单）

执行范围由分诊裁剪：扫描检测 = 阶段 1-5；路由轻量（「更新文档路由」等关键字触发）= 阶段 1-2。

### 阶段 1 · 盘点（全量扫描，不抽样）

① 全仓目录漫游：`ls -R`（排除 `.git/node_modules/dist/build/.venv/__pycache__`），产出实际目录树 + 各顶层目录文件数；② 读「文档清单与定位」与根 `AGENTS.md` §1 目录树、§3 Skill 路由得文档清单；③ 以实际目录树为准判定每个目录"干什么"（`docs-structure` 的 STRUCTURE 只做职责解释，现状以 `ls` 为准），STRUCTURE 与实际不一致即记漂移；④ 每份文档标注机检点（阶段 3 表）+ 其代码扫描范围（阶段 2 映射）；⑤ 旧版本文档检测（强制）：以「本文件「文档清单与定位」+ 根 `AGENTS.md` §1 目录树 + 各 `docs-*` skill 的管辖文档 + STRUCTURE §1 树」为基线，扫 `docs/` 下「不在预期集 / 无对应 skill 管辖 / 与基线命名不一致 / 规范已重命名·合并·删除后残留的旧文档」→ 产出「待处置旧文档清单」（旧文档 → 承接文档或删除）。每次盘点必产出该清单，不看上轮是否已提示。

输出必须含「实际顶层目录清单 + 文件数」，缺此即未完成，不得进入阶段 3。

### 阶段 2 · 路由自适应（维护根 AGENTS.md 的 Skill 路由与 STRUCTURE）

先读「文档清单与定位」、根 `AGENTS.md` §1 目录树与 §3「文档操作 Skill 路由」，再读 `docs/common/STRUCTURE.md` §1 目录树（无该文档则以 `ls` 现状为准）+ `ls` 实际目录，逐目录判定"它是干什么的"（任何目录都算，不限代码——纯文档目录 / 资源目录同样进入映射），产出「文档 ↔ skill」映射；再对账「根 `AGENTS.md` §3 路由表 + 各 `docs-*` skill 的管辖文档 + STRUCTURE §1 目录树」与目录现状，产出双向同步提案——为新增文档补对应 `docs-*` skill 与路由行 / 清理已删文档的路由行与 skill / 调 `docs-structure` 同步 STRUCTURE 目录树；提案交用户确认，确认后落盘并复核「路由表每条都有对应 skill、skill 内相对链接指向的路径真实存在」。

本阶段为必做门槛：无论目录是否变动都必须执行并给出显式结论——输出三件套：① 目录变动结论（`ls` 实际与 STRUCTURE §1 对比，无变动也要写明）；② 文档 ↔ skill 对账表（缺口 = 待补 skill/路由，死项 = 待清理）；③ 双向同步提案（补 + 清理）或"无需变更"结论。三者缺一即未完成；禁止静默跳过。

### 阶段 3 · 机检（grep/ls/diff 按清单执行）

| 机检点                                                                                                                    | 方法                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 文档内 File:Line 引用有效性                                                                                               | 文件存在 + grep 符号存在                                                                         |
| STRUCTURE 目录树与实际目录对比                                                                                            | diff 目录树与 `ls -R`                                                                            |
| openapi.yaml 尾注释计数 vs INBOUND.md §1 端点计数列 vs 代码路由数                                                         | 三方计数对比                                                                                     |
| 交叉引用死链（文档 A 引 文档 B §X，B 无该节）                                                                             | grep 目标文档章节标题                                                                            |
| 实例头部原则块 / 建模方法论残留（「> 【原则】」「决策速查」「领域事件原则」「Q1-Q6」）                                    | `grep -rnE -e '^> 【原则】' -e '决策速查' -e '领域事件原则' -e 'Q1-Q6' docs/` 应为 0             |
| 目录归属口诀例外（STRUCTURE infra/integration 归属判别口诀属合法读者内容，不进全 docs/ 检查）                             | 建模方法论口诀只在域文档禁：docs/L2/domain/ 下域文档另查对象类型判据 / 判断口诀应为 0            |
| BUSINESS 能力行与 DOMAIN Action 清单双向对齐                                                                              | 交叉 grep 能力名 / Action 名                                                                     |
| DOMAIN 方法签名 vs 代码函数签名                                                                                           | grep `def`/`func` 匹配 §3 领域操作方法详情竖表「方法签名」行                                     |
| 目录索引 INDEX.md 一致性（deep-dives / research / outbound-contracts / changes 有 INDEX.md，domain/ 用总文档 §3 清单） | 目录内文件与 INDEX.md 清单表一一对应，无幽灵行 / 无漏登                                          |
| 旧版本文档（规范重命名 / 合并 / 删除后的残留）                                                                            | docs/ 文档不在「文档清单与定位」预期集、或与根 AGENTS.md §1 目录树 / STRUCTURE §1 命名不一致 → 列「待处置」 |

### 阶段 4 · AI 语义核对（逐文档全读，不抽样）

对每份文档，调其管辖的 `docs-*` skill 读取该文档的应然内容，并列出本次已读代码文件清单；逐文件读后对照文档陈述（行为 / 规则 / 流程 / 约束），差异逐条记「文件:位置 / 文档陈述 vs 代码事实」。

禁止抽样（只读 1-2 个代表文件即违规），禁止无 File:Line 佐证的"一致 / 无漂移"结论；输出必须含每文档「已读 N 个文件」+ 文件清单，否则视为没读。

### 阶段 5 · 落清单（扫描产出，不询问不修复）

把阶段 3 机检 + 阶段 4 语义核对检出的差异逐条落成 `.omo/drift/<doc>.md`（格式见 §5）：每条记 位置 / 差异（文档 vs 代码，含 File:Line）/ 漂移原因（AI 判断，如代码重构未同步 / 需求变更 / 实现简化 / 契约理想与实现差距）/ 状态=待修复；用户决断留空——扫描阶段只记录不询问，裁决在分诊 2 处置时发生。

输出：漂移清单 + 路由对账三件套 + 每文档已读文件清单 + 待处置旧文档清单。

## 3. 处置漂移（消费 .omo/drift/ 清单——唯一询问用户处）

1. 读清单：`ls .omo/drift/`；无清单时告知当前无待处理漂移（建议先走分诊 1 扫描产出），结束
2. 逐条分析：按清单「位置 / 差异」重读代码与文档对应位置，校准性质（实现 bug / 文档错 / 契约漂移）、漂移原因与定级（严重：影响 API 契约 / 用户故事验收；轻微）
3. 问用户决断（唯一询问处）：逐条交用户裁决——以文档为准（改代码，需用户二次确认）/ 以代码为准（改文档）/ 逐条判断；裁决写入「用户决断」列
4. 执行处置：按决断修——文档调其管辖的 `docs-*` skill 重新生成受影响节，修后按该 skill 的完成判定验证；实现 bug 只报告不动代码
5. 清账：每修一条立即更新清单状态（已修复）；单文件全部「已修复」后 `rm` 该清单文件（空目录一并删除），完成判定叠加已删章节 §x 零残留

## 4. 文档初始化（docs/ 缺失或残缺，按对应 skill 生成）

适用：项目已装 `docs-*` skill 但 `docs/` 缺失或残缺，用户要求「生成文档」「初始化文档」「按文档 skill 建文档」；或默认对齐检出 `docs/` 缺失时先问用户是否初始化。

1. 缺口盘点：按「文档清单与定位」、根 `AGENTS.md` §1 目录树与 §3 Skill 路由列目标文档，判定 存在 / 缺失 / 空壳；已存在的归分诊 1 对齐（不重建、不覆盖），只补缺口；缺口清单（文档 / 现状 / 建议）交用户确认生成范围
2. 信息源定级：逐份标注来源——代码派生（L2 架构 / L3 契约 / L4 交付 / common，扫描代码库得出）或 用户访谈（L1 产品目标与用户故事，代码推不出）；代码不足以支撑的按访谈处理
3. 顺序铁律（硬约束）：严格自上而下逐层串行——L1、L2、L3、L4，common 最后（贯穿层需综合各层结论）；每层全部文档生成并经用户确认后才进下一层，禁止跳层、乱序、并行（如先 L2 后 L1）。列「文档 / 对应 skill / 信息源 / 顺序」清单交用户确认后动手
4. 逐份生成：生成某层文档前，先读上一层已落盘产物作为输入（下层结论须与上层对齐），再调该文档管辖的 `docs-*` skill——代码派生类扫描代码、访谈类与用户逐条谈定要点——写 `docs/<路径>`，按该 skill 的完成判定验证；谈定一份写一份，不积压、不跳层
5. 收尾：路由自适应复核（新增文档对应根 `AGENTS.md` §3 路由行与 `docs-*` skill；调 `docs-structure` 同步 STRUCTURE）+ 报告（生成清单 / 每份信息源 / 待用户补充项）

## 5. 漂移清单格式（.omo/drift/，扫描产出、处置消费）

发现 code-doc 漂移时按漂移文件各落一清单 `.omo/drift/<doc>.md`（如 `docs/L2/DATA-ARCHITECTURE.md` 的漂移对应 `.omo/drift/DATA-ARCHITECTURE.md`）：

一份清单只承载一个文档的漂移项；一个文件内只有一张表（清单即待办列表）：

- 表头固定六列：`#` / 位置 / 差异（文档 vs 代码）/ 漂移原因 / 用户决断 / 状态（竖线须转义）
- 漂移原因：扫描阶段由 AI 判断记录（代码重构未同步 / 需求变更 / 实现简化 / 契约理想与实现差距等）
- 用户决断：扫描阶段留空（`—`）；处置阶段由用户裁决填入（以文档为准 / 以代码为准 / 逐条）
- 状态枚举仅两态：`待修复`（默认，发现即记）/ `已修复`（修完标记）；符号 `☐`/`☑` 可选前缀——全部已修复即 `rm` 清单文件（空目录一并删除）
- 扫描阶段只记录不询问；处置阶段才问用户决断并回写；每修一条立即更新状态
- 清单在跟踪期入库（团队可见）；完成判定叠加：`grep -rn "§x" docs/ AGENTS.md` 对已删章节零残留

模板：

```markdown
# drift · <doc>

| #   | 位置          | 差异（文档 vs 代码）                              | 漂移原因        | 用户决断   | 状态     |
| --- | ------------- | ------------------------------------------------- | --------------- | ---------- | -------- |
| 1   | §X.Y <章节名> | 文档："<文档陈述>"；代码：<代码事实（File:Line）> | <AI 判断的原因> | —          | ☐ 待修复 |
| 2   | §X.Z <章节名> | 文档："<文档陈述>"；代码：<代码事实（File:Line）> | <原因>          | 以代码为准 | ☑ 已修复 |
```

## 6. 旧版本文档清理与融合（每次检测必提示，用户认可才动）

模板版本演进（文档 skill 重命名 / 合并 / 删除 / 承载形态迁移）会让项目 `docs/` 里出现旧版本文档——它们不在「文档清单与定位」预期集内、无对应 `docs-*` skill 管辖、或与根 `AGENTS.md` §1 目录树 / STRUCTURE §1 命名不一致。

每次检测到旧文档都必须提示并催促用户处置：上轮已提示但未处理的，本轮继续提示（持续到处置为止），不得因"上轮说过"而静默跳过。

处置按「有无新定位承接」二分——先对照「文档清单与定位」，看旧文档的知识是否能落到某份新文档的定位范围内：

- 有新定位承接（旧文档被重命名 / 合并 / 承载形态迁移到新文档）→ 融合：读旧文档与承接文档，调承接文档对应的 `docs-*` skill，把旧文档中仍有效的知识按承接文档的骨架重组写入（吸收进新文档，不是复制粘贴、不是另起占位）；融合后旧文档内容不得在承接文档之外残留。
- 无新定位承接（本版不再需要该文档）→ 删除：确认旧文档知识已无保留价值后删除。

纪律：

- 不得自动迁移或删除——融合与删除都必须取得用户明确认可后执行；用户本次选择不处置 → 记录在案（待处置清单保留 旧文档 / 处置方式 / 承接文档 / 状态），下次检测继续提示。
- 融合走承接文档的 `docs-*` skill（本 skill 不手写文档正文）；删除只针对旧文档文件 / 目录本身。
- 待处置旧文档清单随输出报告一并交付。

已知迁移映射（随模板版本累积，供跨版本旧文档识别）：

| 旧文档                                    | 处置 | 承接                                                            |
| ----------------------------------------- | ---- | --------------------------------------------------------------- |
| `docs/L1/USER-STORY.md`（旧版 L1 用户故事） | 融合 | `docs/L1/BUSINESS.md`（业务流程，含用户故事、验收标准与用户旅程） |

## 7. 输出与边界

输出报告：漂移清单（文件:位置 / 差异 / 判定：漂移或疑似 bug / 处置：已修或待用户裁决）+ 路由对账三件套 + 每文档已读文件清单 + 待处置旧文档清单（旧文档 / 处置方式 / 承接文档 / 用户处置状态）。

边界：只检测、修复、初始化与处置 `docs/**` 文档；不修代码（疑似 bug 交用户裁决）；旧版本文档的融合与删除必须用户逐次认可，不得自动执行（每次检测持续提示直到处置）；不自动 commit/push；`.omo/evidence` 属历史记录不追溯。
