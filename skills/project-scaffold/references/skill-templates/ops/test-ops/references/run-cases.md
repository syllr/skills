# 执行用例

按用户指定的范围，在某个环境逐卡执行、记录问题、汇报。

## 读取

- 读 [test-assets.md](test-assets.md) 确认用例卡与执行台账的落点与命名规则。
- 按本次执行范围，读范围内用例对应的用户故事（`docs/L1/BUSINESS.md`）与领域实体（`docs/L2/domain/`）口径。
- 读 `docs/contracts/inbound/`（对外接口的接口 → 代码映射，断言以代码为准）；工具清单与各工具的环境参数见 `tools-ops` skill
  的类文档。
- 源缺失或冲突时先核实，不臆造接口、实体或环境；缺什么报什么，不自行补默认值。

## 步骤

跑前把下面几项一次问清、一次拿齐，再开始跑；进入执行后不再向用户要任何授权或决策，中途无用户介入。

### 跑前判定与授权

1. 范围确认：问用户本次执行范围（某场景 / 某领域目录 / 指定 <文件> 的 caseN / 某一批）——用户不确定时列出
   `docs/test/test-cases/`（api/<领域实体>/ 与 flow/<用户故事场景>/）下的可用用例；未确认不执行。
2. 环境（逐工具判定）：先问用户「是不是都走 standalone」——是则全部工具都用 standalone；不是则逐工具（或按组）问清各自走哪个环境。环境是
   **工具维度**的：本次范围用到的每个工具都各自定一次环境，可能不同工具不同环境；每条命令按 **该工具**
   类文档「环境参数」表选中该环境那一行拼参数，不读全局环境矩阵。
3. 排序分析：通读范围内用例，按前置条件做依赖分析确定执行顺序——被依赖的用例先行（如查询类用例的前置通常是新建业务对象，新建用例必须先跑）；上游失败是否阻塞下游具体问题具体分析（结构性前置缺失会阻塞，字段级差异一般不阻塞）
4. 策略确认：问用户失败策略——fail-fast（遇失败即停下定位）或全量跑完再逐个定位
5. 浏览器模式确认（仅含 FLOW 卡时）：范围内含 FLOW 卡（流程用例，走页面调用型工具）→ 问用户用有头浏览器（`--headed`，人工旁观；步间默认停留
   1500ms，每步结果可见，`--step-delay` 可调）还是无头（默认，速度优先，不停留）；纯 API 卡范围跳过本步
6. 授权：汇总本次范围内所有需要用户授权的操作（卡里的 `--write` 写操作、删除 / 变更类调用等），一次性向用户拿齐；未获授权的卡本次不跑。

### 执行（无用户介入）

7. 执行：建 todo——按本节步骤 3 顺序逐卡执行（读卡，按卡的前置/执行/期望/数据对账/清理照做——工具命令按该工具类文档「环境参数」表选中该环境那一行拼连接参数，逐条记录
   pass/fail
   与对账证据），按步骤 4 策略处理失败
8. 问题记录：执行中发现以下任一问题 → 即时落测试记录（见下）：用例卡问题（断言无契约支撑 / 命令形态错 / 路径过时 / 前置缺失 /
   表述与实测不符）、被测代码问题（接口行为与契约不符 / 数据落位异常 / 边界未处理）、工具问题（工具缺陷，修工具走 `tools-ops`
   skill）、环境问题（部署/网络/服务不稳定）。
9. 汇报：pass/fail 清单 + 对账证据 + 测试记录问题清单（按类型分组）+ 失败定位

> 环境纪律：环境 **逐工具判定**——本次范围用到的每个工具都要各自定一次环境（跑 10 个用例、用到 10 个工具，就逐工具定 10
> 次），可能不是同一个环境；先问用户是否都走
> standalone，不是则逐工具问清。每条命令按 **该工具**类文档的「环境参数」表选中该环境那一行拼参数，不读全局环境矩阵。

完成判据：全部命令走 `tools-ops` skill 的工具通道，无 curl、无裸命令；断言三源可回溯（状态码 / 字段 / 错误码以接口代码为准，
经 `docs/contracts/inbound/` 的接口 → 代码映射定位，实测校准；依据失效交 `inbound-ops` 修映射，不在本 skill
改代码）；造数据的
Case 含三态清理，环境 host 不写死（走该类文档「环境参数」表）；执行的被测版本已绑定，每条问题有证据与状态枚举，台账只增不删。

## 测试记录（执行发现的问题台账）

位置：`docs/test/test-records/<YYYYMMDD-HHmmss>-<归属对象>.md`——时间戳取写入记录那一刻（命令
`date +%Y%m%d-%H%M%S`，精确到秒），归属对象 = 卡名（如 `FLOW-PROJ-01`）或 环境/工具名；每次执行独立一份文件（不追加、不复用），时间戳保证唯一不重复。

格式：

```markdown
# 测试记录 · <归属对象> · <YYYY-MM-DD HH:mm:ss>

| 被测版本              | 执行范围      | 结论                          |
|-----------------------|---------------|-------------------------------|
| <commit / 构建号>     | <卡名 / 批次> | PASS / PASS（带偏差）/ FAIL   |

| 工具   | 环境   |
|--------|--------|
| <工具> | <环境> |

| #   | 类型     | 位置                    | 现象                         | 证据                | 处理建议   | 状态 |
| --- | -------- | ----------------------- | ---------------------------- | ------------------- | ---------- | ---- |
| 1   | 用例卡   | FLOW-PROJ-01 期望结果   | <卡的问题：断言无契约支撑等> | <证据（契约/实测）> | <改卡建议> | 待修 |
| 2   | 被测代码 | <接口 / 函数 / 文件:行> | <该版本代码的 bug 现象>      | <复现输出 / 日志>   | <修复方向> | 待修 |
```

- 类型枚举与归属：用例卡（卡本身要修，归本 skill 更新卡）/ 被测代码（该版本代码 bug，记录精确版本+位置+复现证据，交开发修复）/
  工具（工具缺陷，修工具走 `tools-ops` skill）/ 环境（部署/网络/服务）
- 被测版本必填：代码 bug 必须绑定版本——修复后可对照「哪个版本起不再复现」
- 状态枚举：待修 / 已修 / 已反馈 / 忽略
- 每条必须有证据（契约位置、实测输出、日志片段）——无证据不记
- 问题修复后更新状态（不删记录，保留台账）

## 联动

- 工具用法与各工具的环境参数归 `tools-ops` skill，用例访问被测系统一律走该 skill 的工具通道。
- 按需部署由 `deploy-ops` skill 执行。
- 断言基准取自 `docs/contracts/inbound/` 的接口 → 代码映射。

## 边界

- 工具实现与调用归 `tools-ops` skill：本 skill 只做执行编排（环境 / 顺序 / 策略 / 记录），不实现工具、不绕过工具直连被测系统。
- 环境参数在各工具类文档的「环境参数」表，本 skill 不另立环境矩阵；`docs/test/` 根下不另设总说明。
