# align-docs — 文档编排器

## 定位与管辖文档

定位：文档体系的总编排器（根 `AGENTS.md` §2.1 差异主动修复）。把「编排 / 对齐 / 处置 / 旧文档处置」拆给各文档 skill 执行——每个
skill 各自管一份文档的读取 / 生成 / 更新 / 校验（管辖关系见根 `AGENTS.md` §3「Skill 路由（三类）」）。本 skill 不生产任何文档正文，只决定调哪些
skill、按什么顺序，并做跨文档一致性核对与漂移分诊；漂移清单的落盘交 `docs-draft`。

前置：项目已安装 A 类 `docs-*`（含 `docs-draft`）与 B 类 `*-ops` skill；未安装时先由 project-scaffold 安装。

## 读取

1. 读根 `AGENTS.md` 作为 L0 基线：文档体系与目录架构（§1）、通用规范（§2）、Skill 路由（§3）。
2. 读下方两张表，确认本体系预期的文档与资产域，以及每份文档归哪个 skill 管。
3. 逐份读该文档的管辖 skill：其「读取」段声明读谁（上游），其 references 里的资产声明（链外域），其「完成判定」。
4. 逐份读该文档管辖范围内的代码与配置，与文档陈述对照。
5. 源缺失或冲突时先核实，不臆造；跨 2 层以上或判定存疑时回 L3 重走整链。

## 产物基线（当前预期）

本体系管理的对象是链内与链外两套基线，链内链外各有一张表。本 skill 只按链内方法改链内文档：沿链判定、逐份对齐、生成与传播 都按本
skill 的流程走。链外的产物域与过程态台账是各自独立的域，不归本体系编排——它们的增删改由用户直接调对应 skill 处理， 本 skill
不判定、不生成、不对齐它们，只在链上某层变化确实牵连到某个链外域时，把该影响写进报告交用户处置。

### 链有两个遍历方向

```text
生成  L1 → L2 → L3   上层先定边界，下层承接
变更  L3 → L2 → L1   事实先变，结论随之
```

L3 是事实起点（目录与文件的现状投影），L1 是抽象结论。任何改动都先落
L3，再沿链向上逐层判定该层事实是否随之变化。链上不另设依赖图——层级编号已经编码了顺序，跨层一致性就是「走到某一层时判定要不要改」，方向单一

`docs/contracts/`、`docs/deployment/`、`docs/test/`、`docs/tools/` 是链外产物域（各有资产），`docs/deep-dives/`、
`docs/research/`
是无资产独立域，`docs/changes/`、`docs/drift/` 是过程态台账；它们都是独立域，不由本 skill 编排。链内只有 L1 / L2 / L3
三层，没有贯穿层，也没有跨层专题文档。

## 生成与更新

生成与更新走同一条流程：先扫 `docs/` 判断缺失与既有，缺失或残缺的按链生成、已有的沿链向上判定并传播。本 skill
不写任何单份正文，只决定调哪些 skill、按什么顺序，并做跨文档一致性核对与漂移分诊。

### 生成（编排：docs/ 缺失或残缺）

适用：`docs/` 缺失或残缺，用户要求「生成文档」「初始化文档」。

1. 缺口盘点：按「链内表」列目标文档，判定 存在 / 缺失 / 空壳；已存在的不重建，只补缺口；缺口清单交用户确认范围。
2. 信息源定级：逐份标注来源——代码派生（L2 架构 / L3 目录）或用户访谈（L1 业务定位、产品能力、用户故事）。代码推不出的一律按访谈处理。
3. 顺序铁律：严格沿链 L1 → L2 → L3 串行；L2 内部序为 domain → 技术架构 → 数据架构 → 应用架构。禁止跳层、乱序、 并行。列「文档 /
   管辖 skill / 信息源 / 生成顺序」清单交用户确认后动手；每份读谁由该 skill 的「读取」段决定。
4. 逐份生成：生成某份前先读其上游已落盘产物作为输入，再调该文档的管辖 skill 写 `docs/<路径>`，按该 skill
   的完成判定验证；谈定一份写一份，不积压。
5. 收尾：调 `docs-structure` 同步目录树与根 `AGENTS.md` §3 路由表（新增文档补行、已删文档清行），再跑「全量对齐」。

### 更新（传播：自 L3 沿链向上逐层判定）

任何改动都从这里进入。判定按链自下而上走，每层只问一句「本层事实是否随之变化」；要改就调该层 skill 改完再走上一层。

| 层 | 判据（什么变了）                                                       | 动作                                                                                                        |
|----|------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------|
| L3 | 目录增删或改名、文件增删或改名、目录职责变化、文档 ↔ 代码映射变化      | `docs-structure` 改 `STRUCTURE.md`                                                                          |
| L2 | 能力与聚合对应关系变化、应用与模块增减、选型与版本变化、表与集合增删改 | `docs-domain` / `docs-application-architecture` / `docs-technology-architecture` / `docs-data-architecture` |
| L1 | 能力增删或状态变化、参与方与角色变化、用户故事与旅程增删改             | `docs-business`                                                                                             |

执行要求：

1. 起点必是 L3：先读 `docs/L3/STRUCTURE.md` 定位改动落在哪个目录 / 文件，该文档与实际不一致即先改它。目录没变也要写明结论
2. 逐层判定，不跳层：每层给出「要改 / 不要改」与依据；判定「要改」就调该层 skill 改完，按该 skill 完成判定验证，再走上一层
   差异的读法与判定依据来自该层 skill 的完成判定，本 skill 不另立一套标准。
3. L2 内部按 domain → 技术架构 → 数据架构 → 应用架构 顺序判定
4. 链外产物不参与层间传播
5. 兜底：本次改动跨 2 层及以上，或任一层判定存疑时，回到第 1 步重走整链，不靠单点判定下结论
6. 全量对齐是独立入口：用户要求「检查漂移」或链上判定不可信时，走「全量对齐」逐份核对。传播不豁免全量，只是不替代它
7. 落台账：把逐条差异（位置、差异、漂移原因）交给 `docs-draft` skill，由它落盘为 `docs/drift/<doc>.md` 清单。本 skill
   不自己写清单正文，只发起调用与汇总；只记录不询问不修复。

输出：本次链式判定结论（逐层要改 / 不要改 + 依据）+ 改动清单 + 待处置旧产物清单（见「旧版本文档清理与融合」）。

## 处置（消费 docs/drift/，唯一询问用户处）

1. 读清单 `ls docs/drift/`；无清单时告知当前无待处理漂移（建议先走「全量对齐」产出），结束。
2. 逐条分析：重读代码与文档对应位置，校准性质（实现 bug / 文档错 / 契约漂移）与严重度（严重：影响接口契约或用户故事验收；轻微）。
3. 问用户决断（唯一询问处）：逐条交用户裁决——以文档为准（改代码，需二次确认）/ 以代码为准（改文档）/ 逐条判断；裁决交
   `docs-draft` 回写到清单「用户决断」列。
4. 执行：文档侧调其管辖 skill 重新生成受影响节，修后按该 skill 完成判定验证；实现 bug 只报告不动代码。
5. 清账：每修一条交 `docs-draft` 把该行状态改为 `已修复`；全部「已修复」后交 `docs-draft` 删除该清单文件与空目录。

清单格式由 `docs-draft` skill 持有（见其 `assets/TEMPLATE.md`），本 skill 不重复定义、不自己编写清单正文。

## 全量对齐（兜底：逐份核对，不抽样）

链式判定不可信、或用户明确要求「检查漂移」时走这里。逐份全读全比，不抽样。

1. 逐份自检：按「链内表」逐行调该文档的管辖 skill，对其目标文档跑完成判定。
2. 逐份核实语义：逐份读该文档管辖范围内的代码 / 配置，与文档陈述逐条对照（行为 / 规则 / 流程 / 约束），差异记「文件:位置 /
   文档陈述 vs 代码事实（含 File:Line）」。格式问题在第 1 步顺带确认，语义差异必须读代码得出。
3. 链序对账：沿链逐对读该层 skill 的「读取」段核其声明的依赖是否成立——上游产物里没有它引用的信息即漂移；本 skill 不另立一份上游口径。
   不自己写清单正文，只发起调用与汇总；只记录不询问不修复。

输出：漂移清单 + 每文档「已读 N 个文件」清单 + 路由对账结论 + 待处置旧产物清单。

## 旧版本文档清理与融合

模板版本演进（skill 重命名 / 合并 / 删除 / 承载形态迁移）会让 `docs/` 出现不在链内表与链外表内的旧版本产物。检出方式：直接读项目
`docs/` 的实际内容，与链内表和链外表逐项对照（链外表连同「资产」列），两张表里都没有的文件或目录即旧产物；检出即提示，上轮已提示未处理的本轮继续提示。

处置按「有无新定位承接」二分：逐个看旧产物实际写了什么，对照两张表的「定位」列，判断它的知识能否落进某份文档的定位范围——

- 有承接 → 融合：调承接文档的管辖 skill，把仍有效的知识按其骨架重组写入（吸收进新文档，不复制粘贴、不另起占位）；融合后旧内容不得在承接文档之外残留。
- 无承接 → 删除：确认知识已无保留价值后删除。

目录级旧产物必须先读完实际内容再定性，判定以内容为准、不以路径为准。命中以下任一即视为有实质内容，一律按「有承接」处理，不得整目录直接删：

- 含单篇文档正文（成篇的架构说明、专题文档、链路时序等）；
- 含索引或收敛标准（目录索引、主题清单、什么值得单列的判定标准等）；
- 含已登记的资产脚本或配置。

只有目录内无实质内容（空目录、或仅剩工具生成的占位文件）时，才按「无承接」删除。旧目录换了新位置（如从 `docs/L2/<子域>/` 迁到
`docs/<新位置>/`）时，
先调新位置的管辖 skill 完成融合，确认新位置已落盘后再删旧目录；新位置还没有管辖 skill 的，先向用户报告并等其决定，不擅自删除，也不自行暂存到别处。

纪律：不得自动迁移或删除，融合与删除都须用户逐次认可；融合走承接文档的 skill（本 skill 不手写正文）；删除只针对旧产物文件 /
目录本身；删除前必须先读完旧产物的实际内容；待处置清单随报告交付。

不预设旧产物到新文档的映射表：旧产物叫什么、装在哪，取决于目标项目装过哪些历史模板版本，一律按实际内容判断；两张表只用于确认「这份知识该落到谁那里」。

## 联动

- 逐份调各文档管辖 skill 执行生成、更新与校验：链内 `docs-*` 与链外 `*-ops`（管辖关系见根 `AGENTS.md` §3）。
- 漂移清单的落盘与清账交 `docs-draft` skill；本 skill 只发起调用与汇总，不写清单正文。
- 链外产物域不归本 skill 编排，其增删改由用户直接调该域管辖 skill；链上某层变化牵连到某链外域时，把影响写进报告交用户处置。

## 完成判定

- 链式判定逐层给出「要改 / 不要改」与依据，无跳层；跨 2 层及以上或任一层判定存疑时已回到 L3 重走整链。
- 全量对齐逐份核对、未抽样；漂移清单已交 `docs-draft` 落盘，格式与状态由该 skill 负责。
- 链内表与 `docs/` 实际内容一致，旧产物已检出并列出待处置清单；融合与删除均经用户逐次认可。
- 输出报告含链式判定结论或漂移清单、每文档已读文件清单、路由对账结论与待处置旧产物清单。

## 边界

- 只做编排、分诊与调度，不生产任何文档正文——层文档交各管辖 skill，漂移清单交 `docs-draft`；不修代码（疑似 bug 交用户裁决）。
- 链外产物域由各自管辖 skill 校验，本 skill 不验资产门禁，也不编排其增删改。
- 旧版本产物的融合与删除须用户逐次认可，不自动执行。
