# docs-business — 业务流程（业务全景 + 需求）

## 定位与管辖文档

- 管辖 `docs/L1/BUSINESS.md`
  （业务流程），一份文档同时承载业务侧与需求侧：业务全景（参与方与角色、业务主线、业务模式、业务规则）、产品能力（图例、能力架构图）、用户故事（清单、详情）、用户旅程（各角色总旅程）。
- 目标文档结构以 [assets/TEMPLATE.md](assets/TEMPLATE.md) 为准，本 skill 不另行维护章节骨架；生成或更新前必须先读取该文件，并严格沿用其中的章节编号、标题层级和结构。
- 本 skill 只提供执行方法与内容规范，不承载项目具体取值；实例文档只写项目业务与需求事实。
- 领域对象的字段、状态机与聚合约束归 `docs-domain` skill；本文档的业务规则只写业务上必须成立的约束，不写领域模型结构。
- 应用与技术边界归 `docs-application-architecture` skill，跨系统接口契约归 `outbound-ops` skill，本文档不写系统划分与接口。
- 业务验收标准由本 skill 定义；测试用例、技术验收与 `docs/test/` 测试资产归 `test-ops` skill。
- 图一律用 D2 / Mermaid / ASCII 代码块写入 Markdown，不贴位图，图旁只标图名、不复制绘制方法；容器式分层图遵循
  `c4-container-diagram` skill，D2 图保留图名、视角、用途和边界等自描述信息。具体图型与内容要求见模板各节生成提示。
- 产品能力及其状态只在本 skill 维护。能力图不列不存在的功能，不记录已砍掉能力或「无 Action」，历史决策归 Git。
- 能力状态默认用实线表示已实现（含本迭代）、虚线表示待规划，必要时可用点线表示中间态；优先级可选核心、支撑、边缘，并与架构图热力色对应，未使用则省略；入口层不参与状态编码。
- 能力与领域操作 Action 是 1:N 映射，Action 详情归 `docs-domain`
  skill。能力域取业务域；被两个及以上垂直能力共用的能力归共享业务服务层，单一业务能力归垂直层，开箱自带且无管理界面的能力标为系统内置。
- 垂直能力之间不互相依赖，只依赖共享业务服务层；横向能力与系统内置能力尽量解耦。
- 角色覆盖产品全部用户角色，并标明系统内与系统外。
- 用户故事是需求最小单元：每个故事只由 Connextra 三段式、Given-When-Then
  验收标准和一张时序图组成，不写元信息小节，也不写页面名称、入口路径等前端细节；单个故事自包含，允许为读者理解而适度重复。
- 文档不设承载文档索引章或相关文档聚合链接章，内容条目不使用顺序编号（US-N / 场景 N / AC-N 等），Mermaid autonumber 不受此限制。

## 读取

- 业务事实只来自用户：用户提供的需求来源（需求文档 / 访谈 / 口头或书面说明）与已落盘的 BUSINESS.md。BUSINESS.md
  的任何业务内容变更都必须有用户给出的信息源或结论，没有就向用户索取，不从代码或下层文档推断。
- `align-docs` skill 是跨文档编排器；本 skill 属 L1，生成前先读取项目宪法作为 L0 基线。
- 生成前读取 L2 的领域模型（`docs-domain`）的业务对象与领域操作、应用架构（`docs-application-architecture`）、 集成契约（
  `outbound-ops`）的关联产物。
- 项目文档按 L1 → L2 → L3 的顺序生成；生成下层文档前先读上层产物。
- 已有 BUSINESS.md 时先提取仍有效的业务事实、能力状态、业务规则、故事与旅程，不沿用已失效的结构或描述。

## 生成与更新

生成与更新走同一条流程：先读模板，再扫目标位置判断有无既有文档或同定位的旧产物，有则更新、无则新建。以下情况都进入本流程：新建、编辑或重建
BUSINESS.md；关联产物变化需要联动更新；用户明确要求生成。

1. 先读取 [assets/TEMPLATE.md](assets/TEMPLATE.md)，以模板顺序和标题层级作为写作基准。
2. 扫描目标位置（`docs/L1/BUSINESS.md` 及其所在目录），判断有无既有 BUSINESS.md 或同定位的旧产物，决定新建还是更新。
3. 读取项目宪法、关联文档和现有 BUSINESS.md 作为一致性与引用基准；业务事实只从用户提供的信息源取得（用户提供的需求文档 /
   说明 / 访谈），缺来源就向用户索取，无来源不更新业务内容，不从代码或下层文档推断业务意图。
4. 先写业务侧（业务全景、产品能力），再写需求侧（用户故事、用户旅程）；需求侧必须与业务侧的能力、参与方对齐。已有文档仅复用仍有效的信息，按模板重新组织。
5. 使用规定格式写入图、表与文字，并让同一事实的图、表和正文保持一致。
6. 每个故事写 Connextra 三段式 + Given-When-Then 验收标准 + 一张时序图。
7. 业务信息一律向用户确认：能力增删与状态、能力域归属、角色划分、故事优先级、业务定性以及任何流程上的变更，都须用户给出信息源或结论；用户未提供时明确告知缺什么，不自行推断。
8. 更新既有文档时：对照模板逐项检查章节、表格和图示，保留仍有效的项目事实，删除下线能力、过期描述和重复内容；业务事实变化时同步更新相关图、表和正文；能力增删、状态变化与
    Action
   变化必须双向一致；角色或故事增删时同步更新参与方与角色表、故事清单、故事详情和用户旅程；增删或迁移内容后删净旧表述并保持编号连续，不保留迁移占位正文；模板要求但当前无内容的固定位置保留标题并留空。
9. 更新涉及能力的领域操作、应用边界、跨系统契约或测试来源时，按联动规则同步处理。
10. 按完成判定逐项校验后交付，不自动 commit 或 push。

## 联动

- `docs-domain` skill：同步领域操作 Action；能力增删、状态变化和 Action 变化必须双向一致。
- `docs-application-architecture` skill：同步能力与模块的关联、应用边界和技术边界。
- `outbound-ops` skill：业务规则中涉及外部集成或外部单据的约束，与接口契约保持一致。
- 高复杂度能力在本章节目录内单列小节展开，不外链到其他目录。
- `docs-technology-architecture` skill：需要解释系统后端技术栈时读取其技术架构。
- `docs-data-architecture` skill：需要展开后端数据存储时读取其数据架构。
- 标为待规划的能力不得在 `docs-domain`、`inbound-ops`、`docs-application-architecture`、`docs-structure` 或 openapi
  中建模或留占位；这些文档新增 Action 时也必须回写能力状态。
- `test-ops` skill：业务能力与用户故事是测试场景来源；新增或调整时同步测试场景；测试用例与测试资产归 `test-ops` skill。
- `align-docs` skill：负责跨文档编排、漂移检测、初始化和旧文档迁移，本 skill 只报告并处理本文档范围内的一致性问题。

## 完成判定

- 实例文档与 [assets/TEMPLATE.md](assets/TEMPLATE.md) 的章节编号、标题层级和固定结构一致，且没有模板未定义的内容。
- 产品能力架构图按入口层 / 业务能力层 / 共享业务服务层分层，垂直能力按能力域分列，共享与系统内置能力在竖条；能力图例独立存在，架构图内没有重复图例，入口层不参与状态编码。
- 能力状态与架构图线型一致；能力对应的领域操作 Action 可追溯到 `docs-domain`。
- 参与方与角色表覆盖产品全部用户角色，标明系统内与系统外，且不含中间件与基础设施供应商（对象存储 / GPU / 模型仓库等归技术架构）。
- 业务主线图为跨角色 sequenceDiagram，每个阶段一条自环消息，不设系统泳道也不画跨泳道消息，不出现系统名、平台名或实现说明；与
  §4 单角色旅程分工清晰（主线只画阶段，不展开 UI 状态与后端调用）。
- 业务规则集中登记且编号唯一、不复用；规则只写业务上必须成立的约束，不含实现方案与技术选型。
- 横向、垂直与系统内置能力识别正确，依赖方向符合业务解耦约束。
- 故事清单中的每个故事在故事详情中有且仅有一节，角色分组一致，无遗漏或重复。
- 每个故事都带 Given-When-Then 验收标准和一张时序图，且不出现页面名称与入口路径。
- 每个系统内角色都有总旅程图，系统外角色不生成系统旅程图。
- 总旅程与故事时序图都满足三角色、完整链路和系统泳道不含 UI 的约束，L1 未展开 L2、L3 术语。
- 内容条目无顺序编号，文档无承载文档索引章或相关文档聚合链接章。
- 全部业务内容都有用户提供的信息源或明确确认，不含从代码、下层文档或 AI 自身推断得出的业务结论。

## 边界

- 业务事实来源只能是用户：没有用户给出的信息源或结论时，不得新增或改写 `BUSINESS.md` 的业务内容。
