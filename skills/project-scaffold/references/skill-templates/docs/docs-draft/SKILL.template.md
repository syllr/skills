# docs-draft — 漂移清单

## 定位与管辖文档

`docs/drift/` 是漂移清单目录，一份清单承载一个贯穿链路的问题/功能点（可跨多个被漂移文档），目录内不出现清单以外的文件。本
skill 是该目录清单的落盘、更新与清账入口，有两个功能：

- 记录 / 更新漂移：把 change 或 align-docs 给出的逐条差异落盘成清单，或做增量更新；无需用户授权。
- 清理漂移：逐条问用户怎么改（改文档 / 改代码 / 两个都改），按其回答真正执行修复——改代码或改文档，把代码与文档的不一致改到一致；必须经用户授权。

漂移的记录与修复都收口在本 skill：漂移只由站在全局视角的 change 与 align-docs 发起，其他 skill 不发起漂移；发起方给出逐条差异，本
skill 记录并收口修复。

- 目标文档结构以 [assets/TEMPLATE.md](assets/TEMPLATE.md) 为准，本 skill
  不另行维护章节骨架；生成或重建清单前先读该模板，按其中结构与文件命名落盘；字段规则见「记录与更新」。
- 差异判定与严重度校准归发起方（change / align-docs），本 skill 不重新判定。

每份清单自带两层状态：漂移点级的 `待修复` / `已修复`，以及 frontmatter 的清单级 `未清理` / `已清理`。全部漂移点修复后先把清单状态置
`已清理`，再删除文件——清单不存在即视为已清，消费方据此放行。

前置：发起方已完成差异判定并给出逐条差异。

## 读取

1. 先读 [assets/TEMPLATE.md](assets/TEMPLATE.md)，确认结构与文件命名。
2. 列出 `docs/drift/` 确定在途清单；已有清单读取全文，保留仍未修复的漂移点。
3. 读发起方给出的逐条差异（文档、位置、差异、漂移原因），核对其与发起方判定一致。
4. 检查清单当前状态、已修复的漂移点与实际进展是否一致。

## 记录与更新

记录与更新走同一条流程：先读模板，再扫目标位置判断有无既有清单或同定位的旧产物，有则更新、无则新建。差异由发起方判定后交给本
skill 落盘，本 skill 不重新判定。记录与更新无需用户授权。

1. 先读 [assets/TEMPLATE.md](assets/TEMPLATE.md)，确认结构（H1、文档节、漂移点子节）与文件命名；再扫描 `docs/drift/`
   判断该问题/功能点是否已有清单。
2. 文件名由发起方给出，按其给出的名字落盘；本 skill 不自行命名。
3. 无既有清单：按模板逐节新建写入漂移点。
4. 有既有清单：读取旧内容，按被漂移文档与位置做增量追加或结构重建，保留仍未修复的点；已修复的点不重开。
5. 按被漂移文档分节（`## {文档相对路径}`），每个漂移点一个子节（`### {序号}. {位置}`）；`{序号}` 在整篇内从 1
   连续递增、不复用、删除也不重排；位置写到章节或符号；每个子节写清差异（并排写出文档陈述与代码事实，代码侧带 `File:Line`
   ）、漂移原因（取 代码重构未同步 / 需求变更 / 实现简化 / 契约理想与实现差距 等，一句话说清）与状态（一律 `待修复`
   ）；发起方未给出的信息不补造，位置或代码事实缺失时先退回发起方问清，不自行推断。
6. 复读清单，核对文件名、节标题、子节编号连续、每个子节三要素齐全、漂移点与清单两级状态合法，并报告落盘清单。

## 清理

清理必须由用户显式授权，一次清理一次授权；未授权不得改动任何代码或文档。授权后逐条执行：

1. 逐条问用户怎么改：改文档 / 改代码 / 两个都改；用户回答后立即执行，不自行决定。
2. 只做让代码与文档一致的最小改动，不夹带重构、不改与漂移无关的内容；改完立即把该漂移点状态置 `已修复`。
3. 涉及文档正文的改动按该文档管辖 skill 的骨架与规范落地（管辖关系见根 `AGENTS.md` §3），保证改动后仍符合该文档格式。
4. 全部漂移点状态为 `已修复` 后，把 frontmatter 清单状态置 `已清理`，随即删除该清单文件，空目录一并删除。
5. 报告本次清理改动的代码与文档，并复查目录内无残留的 `已清理` 清单。

## 联动

- 差异判定与严重度校准归发起方（change / align-docs）；怎么改由用户逐条确定；执行由本 skill 落地。
- 文档正文的常规生成、更新与重建归该文档的管辖 skill（管辖关系见根 `AGENTS.md` §3）；本 skill 仅在漂移清理时按清单做一致性改动。
- 发现差异实为实现 bug 时退回发起方，不由本 skill 转交代码修改。
- 清理涉及的改动需要验证时，经 `tools-ops`（工具访问）与 `test-ops`（验收）skill。

## 完成判定

- 每份清单的文件命名、frontmatter
  清单状态、文档节与漂移点子节结构、状态取值均符合 [assets/TEMPLATE.md](assets/TEMPLATE.md)。
- 记录 / 更新阶段：每个漂移点的文档与位置可定位到具体文件与位置，代码事实带 `File:Line`；状态只取 `待修复`，无凭空补造。
- 清理阶段：每个漂移点都已逐条问过用户并按其回答执行，改动只为消除代码与文档的不一致；已获用户授权。
- 目录内无状态为 `已清理` 的残留清单，清空后文件与空目录已删除；清单文件不存在即视为该问题漂移已清。

## 边界

- 只做漂移的记录与清理：不重新判定差异、不校准严重度；判定一律退回发起方。
- 记录 / 更新无需授权；清理必须经用户授权，不自动清理、不未授权改动代码或文档。
- 清理只做消除不一致的最小改动，不做重构、不改与漂移无关的内容。
- 清单是过程态，不沉淀定型知识，也不作为永久决策记录。
