# docs-research — 选型与验证调研文档

## 定位与管辖文档

本 skill 负责 docs/L2/research/ 下的选型、对比与技术验证调研单篇。每篇单篇只承载一个调研主题的完整论证，层归属为
L2；目录内不设索引文件；最终选型结论回写技术架构文档。

生成或更新任何产物前，先读取 [assets/TEMPLATE.md](assets/TEMPLATE.md)，按其中对应产物的骨架写入；本文件不重复目标文档的章节结构。跨层编排和漂移处理由
align-docs skill 统一调度。

## 读取

- 读取目标调研及目录内其他调研，确认本次要新增、更新、合并还是删除的文件。
- 读取技术架构文档 docs-technology-architecture 的现有结论、约束和关联章节，作为调研的输入与结论去向。
- 读取候选官网、项目代码、部署或验证环境资料、测试数据和可复现产物；每项外部事实保留来源链接或 File:Line。
- 读取既有调研时提取有效的对比、验证、成本和风险事实，按模板重建，不把文档演进历史写回正文。
- 候选、验证环境或结论依据缺失时先报告，不用推测填充证据。

## 生成流程

1. 单篇使用 kebab-case 文件名，并先读取模板中对应产物的骨架。
2. 扫描候选来源、对比维度、技术架构结论和项目验证环境，确定调研问题与可验证目标。
3. 按模板组织背景、候选对比、POC、成本、风险合规和结论；对比表是候选与维度的主记录。
4. POC 至少覆盖代码、文档、流程设计和性能等验证维度；未覆盖的维度显式记录状态与原因，不用空泛文字替代证据。
5. 评估接入、运维、许可证成本以及许可证、数据、供应商锁定风险；没有结论时先补充依据。
6. 仅在候选或验证维度不足、目标不可判定、成本数据缺失或推荐存在真实分歧时询问用户。
7. 生成后把最终推荐和选型理由同步到 docs-technology-architecture。

## 更新流程

1. 读取旧调研、模板、技术架构结论和全部验证源，建立变更清单。
2. 对照候选版本、代码、验证环境、成本与风险依据，区分仍有效结论和已失效证据。
3. 更新单篇的对比、验证结果、成本、风险、结论及附录证据；推荐变化时同步技术架构对应结论。
4. 新增、删除、改名或合并调研时，核对目录内无残留旧文件，并检查引用该调研的文档无死链。
5. 重新执行完成判定并检查与 docs-technology-architecture 的单链关系。

## 联动

- 技术架构中的选型约束、存储或基础设施结论变化时，读取 docs-technology-architecture 并更新相关调研。
- 调研推荐变化时，将最终选型结论写回 docs-technology-architecture；调研保留论证过程，结论不反向复制到其它实现文档。
- 候选代码、接口或部署验证变化时，按实际来源更新证据和复现信息。
- 目录新增、删除或合并调研时，由 align-docs skill 处理跨文档引用和漂移核对。
- 研究证据、文档合并和改名等演进信息遵循项目文档约定，不在正文重复维护变更记录。

## 完成判定

格式与结构纪律（正文无加粗与 emoji、无 SSOT 或单一事实源字样、无模板说明与未替换元变量、图为 D2 / Mermaid / ASCII
代码块而无位图、无治理套话与固定元信息、章节编号连续不跳号、相对链接可解析、跨文档章节引用无死链、标题层级与骨架 模板一致、不补写
frontmatter）见根 `AGENTS.md` §2.8，各文档不重复列出；以下为本文档专有判定，全部通过才算完成。

- 单篇符合 [assets/TEMPLATE.md](assets/TEMPLATE.md) 的结构、标题层级和链接要求。
- 单篇围绕一个主题，候选与对比维度有明确依据；单候选例外和多维度验证均有可复现证据。
- POC 的验证范围、环境、结果和复现方式完整，未覆盖项有明确状态与原因。
- 成本、风险与合规均有内容或依据，结论能追溯到对比和验证证据。
- 最终推荐已正确写回 docs-technology-architecture，调研与结论之间保持单链关系。

## 边界

- 只维护 docs/L2/research/ 下的调研单篇；技术架构选型结论归 docs-technology-architecture，跨文档编排归 align-docs skill。
- 一篇调研只承载一个选型、对比或技术验证主题；不在目录内新建索引文件，不复制单篇正文。
- 技术架构文档只保留调研结论的引用与落点，调研过程、候选证据和验证细节不复制到技术架构正文。
- POC 或验证缺失时不得把未经验证的内容写成确定结论；证据必须能回到代码、官方来源或可复现产物。
- 图示格式遵循 align-docs skill 的约定，项目另有约定时按项目约定执行。
- 跨文档使用相对 Markdown 链接；文档合并、改名等演进历史归 Git log；不写固定元信息表或变更记录，不自动修改业务代码，不自动
  commit 或 push。
