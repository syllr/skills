## 1. 最高原则（唯一最终目的）

> 宪法的**最终目的只有一个：降低系统复杂度**。所有其他原则、规范都是为实现这个目的的手段。

### 1.1 复杂度的定义

> 复杂度 = 让系统难以理解和修改的任何事物。它来自两个根源：**模糊性**与**依赖性**（详见 1.2 / 1.3）。

**复杂度症状**（用于识别系统是否复杂）：① 改一处需连带改多处（变更放大）；② 理解某个模块需先学习大量背景（认知负荷高）；③ 找不到关键信息的入口（信息缺失/不可达）。任一症状出现即存在复杂度，按 §2 手段处理。

**复杂度来源（分析纪律）**：复杂度按**来源**分两类，**讨论/设计任何问题前先判断复杂度来自哪里**——两者处理手段完全不同，混淆会选错方案：

| 来源           | 是什么                       | 例子                           | 处理方向                     |
| -------------- | ---------------------------- | ------------------------------ | ---------------------------- |
| **技术复杂度** | 性能、并发、可用性等工程挑战 | 高并发、缓存、限流、吞吐       | 技术手段（框架/中间件/架构） |
| **业务复杂度** | 需求纠缠、规则复杂、概念混乱 | 算力扣减必须记流水、余额不为负 | DDD 领域建模                 |

> 判断基准：这个问题**难在技术**（工程挑战）还是**难在业务**（规则/概念纠缠）？技术复杂多用工程手段，业务复杂多用领域建模。两者正交（一个系统可同时有两类复杂度），逐项分析避免一刀切。

### 1.2 模糊性

> **定义**：重要信息不明显、难以获取——需要知道某事，但找不到途径获知，甚至不知道存在问题。

| 维度     | 说明                                                                   |
| -------- | ---------------------------------------------------------------------- |
| 本质     | 信息缺失或难以获取，知识隐藏在代码/文档之外                            |
| 症状     | 认知负荷（需要大量学习才能动手）、未知的未知（不知道该改什么）         |
| 来源     | 命名歧义、注释缺失、文档不足、信息重复漂移、异常路径隐式、设计意图丢失 |
| 消除手段 | §2 引言分类 A：SSOT（§2.2）                                            |

**例子**：一个变量叫 `count` 却不知单位是"秒"还是"次"；一个接口不写注释，调用者必须读实现才能用——都是模糊性。

### 1.3 依赖性

> **定义**：代码无法孤立地理解和修改——改一处必须连带考虑/修改多处。

| 维度     | 说明                                                              |
| -------- | ----------------------------------------------------------------- |
| 本质     | 模块/对象之间存在隐式或强耦合，无法单独理解                       |
| 症状     | 变更放大（小改动需改多处）、认知负荷                              |
| 来源     | 模块间直接引用、跨层依赖、透传、接口耦合、隐式共享状态            |
| 消除手段 | §2 引言分类 B：模块设计（§2.1）、领域建模（§2.3）、分层约束（§3） |

**例子**：网站背景色在每个页面写死，改色需改所有页面；订单对象直接持有另一聚合的对象引用——都是依赖性。

### 1.4 复杂度底线（价值观声明）

> 与最高目的直接相关的**不可违反底线**（价值观声明，非可检查条款）：对每次提交的小复杂度增加不搞"就这一次"——单次依赖/模糊项也要处理（复杂性是增量堆积的，必须持续控制）。具体执行见 S4（差异主动修复）。

### 1.5 设计原则：架构与代码共同演进（Co-Evolution）

> **架构与代码共同演进、双向驱动**——架构设计指导代码，代码实现反哺架构，**无先后之分**。让架构随每次迭代自动演进，避免"设计先行、纸上谈兵"。
>
> **闭环（双向）**：
>
> 1. **架构指导代码**：按当前架构原则（分层单向依赖、上下文分目录）编写代码
> 2. **代码反哺架构**：实现中发现架构不再匹配 → 调整架构（上下文重划、模式修正）
> 3. **对照模式审视**：用 DDD 战略/战术模式（9 种上下文映射、聚合边界）审视代码与架构，找出偏移点（该加 ACL 的、该拆聚合的）
> 4. **沉淀**：把演进后的架构沉淀到 DOMAIN-MODEL（领域建模）/ ADR（决策）；发现新原则再回写宪法
>
> **迭代收敛偏移（核心）**：每次迭代做两件事——
>
> - **收敛老偏移**：排查并修复已有功能中"架构与代码漂移"处（对齐，不让老的偏移累积）
> - **抑制新偏移**：新功能尽量少引入偏移（写前对照架构原则，写完审视）
>
> **长期保证**：只要每次迭代都收敛老偏移、并尽量减少新偏移，整体就能**持续收敛、最终不偏移**——演进方向始终对齐架构。
>
> **建模优化信号（何时触发重划边界）**：审视代码时，以下信号 = **领域建模/边界划分有偏移**，触发「战略重划子域/上下文」：
>
> - **跨上下文传很多信息**（传递字段过多、参数列表冗长）
> - **跨上下文需额外查询**（拿到 ID 后还要去 Infra/Integration 补查）
> - **跨上下文强耦合**（频繁互相 import、改一处连带改多处）
>
> **处理原则**：**战术上**先临时处理（传多字段 / 先查一次，跑通即可，记 TECHDEBT）；**战略上**重新划分子域/限界上下文根治（这是建模偏移，不是代码问题）。具体 DDD 手段与演进决策记 ADR。
>
> **关键**：上下文关系（SK 共享 / C-S 上下游 / ACL 防腐）是**架构与代码共同演进的自然结果**，不是编码前的蓝图——双向驱动、迭代对齐。具体分析流程记 ADR。

## 2. 设计规范（手段的唯一表达地）

> **手段与目的**：宪法中「降低复杂度」的手段（§1 最高原则）分布在 **§2-§3**。按消除对象分两类组织：
>
> - **A 消除模糊性**（让信息明显、知识可获取）：单一事实源 SSOT（§2.2）
> - **B 降低依赖性**（让代码可孤立理解和修改）：模块设计（§2.1）、领域建模（§2.3）、分层约束（§3）
>
> 每条规范后标注【检查方式】，用于代码审查/AI 自检时验证。

### 2.1 架构的两个维度（同层解耦 + 跨层分层）

> **系统是立体的**：一个项目/系统要描述清楚，必须从两个方向组织——**横向**（同一层内，业务与业务之间如何解耦）和**纵向**（层与层之间如何组织）。

| 方向                 | 回答什么问题                             | 怎么做                                               | 对应章节       |
| -------------------- | ---------------------------------------- | ---------------------------------------------------- | -------------- |
| **横向（同层解耦）** | 同一个层内，业务和业务之间如何不互相纠缠 | 先分出要做哪些事 → 把事切成模块 → **高内聚低耦合**   | §2.1（D 系列） |
| **纵向（跨层分层）** | 层与层之间如何组织、依赖如何单向         | 某个模块/业务复杂到一定程度 → **重新抽象出一个新层** | §3 分层约束    |

**递归演进（两个方向的关系）**：

```
先分模块（横向）→ 某个模块变复杂 → 分层（纵向）→ 新层内再分模块（横向）→ 再复杂再分层（纵向）→ …
```

- 复杂度是**递归涌现**的，不是一开始就能规划完——这正是「动态分层」「最小建模起步」等"按需演进"原则的根本原因
- 两个方向缺一不可：只分层不拆模块 → 层内大泥球；只拆模块不分层 → 平面铺开无法承载深度

**横向维度的实现：高内聚、低耦合**（模块设计，具体规则见下方 D 系列）：

| #   | 规范                                                                                                                                                                                                                                                                                | 检查方式                                                                 |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| D1  | **深模块**：接口简单程度必须显著低于实现复杂程度；浅模块（接口≈实现）须给出理由或直接内联                                                                                                                                                                                           | 审查：新模块的接口方法数 vs 实现复杂度                                   |
| D2  | **信息隐藏**：每个模块封装设计决策；同一知识出现在多个模块 = 信息泄露，必须合并或提取封装                                                                                                                                                                                           | 审查：同一常量/格式/决策是否在多处出现                                   |
| D3  | **按知识域拆，不按时间顺序拆**：类的边界 = 知识边界，不是流程步骤——不得按"读→解析→存"这类执行时序拆类（同一知识被切碎到多个类 = 信息泄露），把共享同一知识的所有逻辑收进一个类                                                                                                      | 审查：类名是否暗示执行步骤（读取/解析/预处理）/ 改一处规则是否要改多个类 |
| D4  | **通用与专用分离**：通用机制内不得混入专用代码（专用逻辑放使用方）；接口满足当前需求但可复用                                                                                                                                                                                        | 审查：工具类是否内嵌单一用途逻辑                                         |
| D5  | **禁止浅模块**：禁止透传方法（只转发不做事）、禁止"为小而小"的拆分（多类症）、禁止仅单调用点的薄方法——浅模块应内联或加功能变深                                                                                                                                                      | 审查：方法是否只是转发 / 类是否只有单一调用者                            |
| D6  | **禁止透传变量**：新参数不得贯穿多层签名传递；全局状态统一收敛到 Context 对象                                                                                                                                                                                                       | 审查：参数是否连续多层同名传递                                           |
| D7  | **接口简单 > 实现简单**：把不可避免的复杂性下沉到模块内部；新增配置项前自问"调用者能比我定出更好的值吗？"不能则内部自动处理                                                                                                                                                         | 审查：新增配置项时有无自问记录                                           |
| D8  | **开闭原则（OCP）**：对扩展开放、对修改关闭——新需求通过新增（实现/扩展/策略）满足，不修改已有逻辑                                                                                                                                                                                   | 审查：新增需求是否改动已有代码                                           |
| D9  | **接口隔离（ISP）**：客户端不应依赖它不使用的能力——接口按调用方需求拆分，避免"大而全"                                                                                                                                                                                               | 审查：接口是否有用不到的成员                                             |
| D10 | **接口与多态（何时用接口）**：用接口**减少依赖**（调用方定义接口，被调用方依赖调用方——控制反转），但**不在聚合/值对象内部滥用**——接口只在**层边界**（domain/infra 分界）与**上下文边界**（跨上下文 contract）使用；同一聚合/值对象内部直接调，不为每个方法建接口（避免类/方法爆炸） | 审查：接口是否在边界层（domain/contract）/ 是否在聚合内部滥用接口        |
| D11 | **读写分离（目的）**：**读尽可能简单**——直接读存储层数据，只做无业务意义的字段转换；**写必须走聚合入口**——通过聚合根方法写入，保证业务规则。读走值对象/DTO，写走聚合                                                                                                                | 审查：读是否绕开聚合直接查存储 / 写是否通过聚合根                        |

> 纵向维度的实现（分层约束）见 §3。

### 2.2 单一事实源（SSOT）

> 手段：为实现「降低复杂度」而消除信息重复与漂移（A 消除模糊性）。
>
> **单一事实源不是只指文档**——它覆盖项目里所有信息载体（代码 / 注释 / 文档）之间的**冲突裁决标准**：

| 信息载体之间 | 冲突时以谁为准                                                     |
| ------------ | ------------------------------------------------------------------ |
| 代码 与 代码 | 以运行正确且最新合入的代码为准（Git 历史裁定）                     |
| 代码 与 注释 | **以代码为准**——注释必须反映代码，注释与代码不符即注释过时，改注释 |
| 代码 与 文档 | **以代码为准**——文档必须反映代码，文档与代码不符即文档过时，改文档 |
| 注释 与 注释 | 以代码为准 + 就近原则（离代码越近的注释越可信）                    |
| 文档 与 文档 | 以代码为准 + SSOT（同一信息只在一个文档维护，重复处引用不复制）    |

**核心原则：代码是唯一事实（Code is the Source of Truth）**——文档和注释是代码的投影（不是独立真相），与代码冲突时改文档/注释而非代码；代码本身之间的冲突由 Git 裁决。

| #    | 规范                                                                                                                                                                                                                                                                                                                                                                     | 检查方式                                                                                             |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| S1   | **代码是唯一事实**：文档和注释必须反映代码；任何载体与代码冲突时，改文档/注释而非代码                                                                                                                                                                                                                                                                                    | 审查：文档/注释是否与代码矛盾                                                                        |
| S2   | **同一信息只在一个文档维护**：其他文档引用不复制（复制必然漂移）；发现重复 → 归并到唯一源，其余改为引用                                                                                                                                                                                                                                                                  | 审查：同一信息是否在多处重复书写                                                                     |
| S2.1 | **文档间引用单向向下 + 精简提及**：文档间的**可点击导航链接只允许上层 → 下层**（L0/L1 可链 L2/L3/L4，下层不链回上层）。下层引用上层内容时**只做精简文字提及**（如「SSOT」「见宪法」），不写上层文档的路径/章节锚点——**宪法（L0）全局加载**（跨任务/跨 Agent 上下文恒有），读者无需跳转即可理解；业务内容 SSOT 在上层，下层引用不复制。同级（同层）文档间引用属协作，允许 | 审查：下层文档是否出现 `docs/L0/…` 或「CONSTITUTION §x」类精确锚点；导航链接是否下层→上层            |
| S3   | **注释就近原则**：注释描述它旁边的代码；离代码越远的信息越容易过时，关键注释必须紧贴代码                                                                                                                                                                                                                                                                                 | 审查：注释与代码的距离是否过大                                                                       |
| S4   | **差异主动修复**：执行任何操作（读取/变更）时发现文档/注释与代码有差异 → **主动修复文档/注释**（即使与本次功能无关，无需用户授权——不影响运行）                                                                                                                                                                                                                           | 检查：发现差异即修，不积压                                                                           |
| S5   | **差异分诊（对齐机制，即业界 Bug Triage）**：文档/注释与代码有差异时，按「自动化优先 → 默认以代码为准 → 漂移定级 → Bug 例外」四步分诊（流程见下方）                                                                                                                                                                                                                      | 审查：差异归属判断（bug vs 漂移）+ 是否用户介入 + 自动化是否可用                                     |
| S6   | **文档/注释当前态**：永远表现**当前设计意图**（G），不写因果链（不记录"以前是什么/为什么改"）；更新只写预期值；历史/原因归 TECHDEBT（技术债）、ADR（决策原因）                                                                                                                                                                                                           | 审查：文档/注释是否含过时历史信息                                                                    |
| S7   | **文档与代码同交付（底线）**：任何实质代码变更（新增功能/修改逻辑/架构调整），会话结束前必须同步文档——文档不是可选项，是交付物的一部分                                                                                                                                                                                                                                   | 审查：代码变更是否漏同步文档                                                                         |
| S8   | **表达规范·不用 emoji**：文档/注释/规则文件/提示词**不用 emoji**（[依据与例外](#s8-依据)）—— emoji 在 LLM 视角下 token 成本高、语义多义、跨平台渲染不一致、属装饰性冗余（违反 S2 SSOT）。例外：UI 状态装饰（消息/通知）、人类对话沟通                                                                                                                                    | 自动：`grep -P "[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]" <文档>` → 命中即违规；人工：通读确认无 emoji |

**差异分诊流程（S5 执行细则）**：

```
发现 代码/注释/文档 有差异
  → 先判是否为 Bug（④）；非 Bug 才走②③
  ├─ ① 自动化优先：能由工具自动生成/校验的对齐（如从代码生成文档、链接/示例校验）
  │     → 直接自动化，不走分诊（无自动化工具时跳过此步）
  ├─ ② 默认以代码为准：AI 自主修复文档/注释去匹配代码
  │     （不写死"先改代码还是先改文档"的先后；文档改错代价低可放心对齐；目标让三者离散度收敛）
  ├─ ③ 漂移定级：严重漂移（误导理解/影响使用）优先修；轻微漂移（措辞/表述）顺手修
  └─ ④ 唯一例外 = Bug：代码实现偏离文档真实意图（文档真实反映用户需求，代码写错）
        → 必须用户介入判断（Bug Triage 的"确认"环节）
        → 用户认可才修代码（文档整体意思不变，可微调）；用户不认可则按文档为准修文档
```

#### S8 依据：「不用 emoji」的工程根据

> 此节是 S8 的「为什么」——AI 不知道依据就容易在生成时偷懒加 emoji。

| 维度              | 影响          | 说明                                                                                                             |
| ----------------- | ------------- | ---------------------------------------------------------------------------------------------------------------- |
| **Token 成本**    | ❌ 高         | 1 个 emoji 通常拆成 1-5 个 subword token，**消耗 token 但不增加信息量**（emoji 的"含义"对 LLM 不比纯文本更精确） |
| **语义精度**      | ❌ 低         | emoji 含义多义——同符号在不同系统/文化/上下文含义不同（如 🌚 表尴尬或阴暗）                                       |
| **AI 解读稳定性** | ❌ 波动大     | 同一 prompt 在不同模型/版本下解读不一致；纯文本 + 标记符号（如 `[ ]`/`[x]`）远比 ✅/❌ 稳定                      |
| **跨平台渲染**    | ❌ 不一致     | 不同系统 emoji 颜色/形状不同（红心 ❤️ vs 🤍），影响可访问性和视觉一致性                                          |
| **SSOT 违反**     | ❌ 装饰性冗余 | emoji 是"非语义视觉装饰"，同一信息（语义）已在纯文本中表达，emoji 重复了一层（违反 S2）                          |
| **可访问性**      | ❌ 差         | 屏幕阅读器读 emoji 时输出冗长描述（如"红色心形 emoji"），无障碍体验差                                            |

**例外（允许用 emoji）**：

- **UI 状态装饰**：消息/通知的图标（如系统通知"🎉 新功能上线"）
- **人类对话沟通**：Slack/邮件/IM 中适度传达情绪
- **不属于此规则**：Mermaid 图节点标签（属于图，不是文档文档）

### 2.3 领域建模（动态演进，最小建模起步）

> 领域建模是**手段不是目的**：目标是让业务规则清晰可表达、可演进。采用**最小建模起步、按需演进加深**原则——简单项目不做完整领域建模（ER 图 + 数据字典足够）；业务不变量复杂到现有表达说不清时，才按演进信号逐级引入领域建模。
>
> **战略设计与战术设计**：领域建模分两层，**先战略后战术**——
>
> | 层           | 关注点                                    | 内容                                                  |
> | ------------ | ----------------------------------------- | ----------------------------------------------------- |
> | **战略设计** | **Big Picture**：系统多大、几块、块怎么连 | 子域划分、限界上下文、上下文映射（§2.3.4 阶段 1-2）   |
> | **战术设计** | **流程细节**：块内部怎么组织              | 聚合、实体、值对象、领域服务、领域事件（§2.3.1 构件） |
>
> 战略定边界（地图），战术落地规则（街景）——先战略后战术，避免"战术先行、战略缺位"（上来就写聚合却不知上下文边界）。
>
> **语言/框架无关**：本节全部内容适用于任何语言、任何框架——描述的是**业务建模的本质**（业务对象、业务规则、业务边界），不涉及任何技术栈的特定实现（ORM/对象映射/持久化框架等均不在本节讨论范围）。

#### 2.3.1 建模构件（按需引入，深度逐级加深）

| 构件                              | 定义                                                                     | 何时引入                                      |
| --------------------------------- | ------------------------------------------------------------------------ | --------------------------------------------- |
| **实体（Entity）**                | 有唯一身份、有生命周期、状态可变的对象                                   | 业务对象需要身份识别时（如订单、用户）        |
| **值对象（Value Object）**        | 无身份、只靠属性组合有意义、**不可变**的对象（如金额、日期区间）         | 出现"属性组"概念时；修改 = 新建替换而非原地改 |
| **聚合（Aggregate）+ 聚合根**     | 可视为单一单元的一组领域对象；根保证聚合内不变量；**外部只能引用聚合根** | 出现强一致的对象组合时（如订单+订单行）       |
| **领域服务（Domain Service）**    | 不属于任何对象、无状态的操作（如转账、结算）                             | 操作无法归属到现有实体/值对象时               |
| **领域事件（Domain Event）**      | 过去时命名（OrderPaid）、不可变、记录"已发生的事实"；聚合间通信机制      | 跨聚合/跨上下文需要解耦协调时                 |
| **限界上下文（Bounded Context）** | 模型统一性的边界；同名词在不同上下文可有不同含义                         | 多团队/多系统/模型冲突时                      |
| **持久化边界（Repository）**      | 领域模型与存储的边界；是契约不是具体存储实现                             | 需要持久化领域对象时                          |

#### 2.3.2 建模规则

| #   | 规范                                                                                                                                         | 检查方式                         |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| M1  | **领域对象承载行为**：业务规则应内聚到它所属的业务对象上（如 `订单.支付()` 而非暴露状态让外部改）；禁止"只有数据的对象 + 全部逻辑堆在服务层" | 审查：业务对象是否有业务行为方法 |
| M2  | **聚合边界**：跨聚合只按 ID 引用，不持有对象引用；一次事务/一次操作只改一个聚合                                                              | 审查：聚合间是否直接引用对象     |
| M3  | **聚合内强一致、跨聚合最终一致**：可容忍短暂不一致的规则拆到不同聚合，用领域事件协调                                                         | 审查：操作边界是否跨聚合         |
| M4  | **不变量驱动聚合边界**：必须原子性同真的规则放同一聚合；否则拆开                                                                             | 审查：聚合边界理由               |
| M5  | **存储模型 ≠ 领域模型**：领域模型表达业务语义与规则；存储结构表达存取效率——两者可以不同，领域模型不依赖存储细节                              | 审查：领域逻辑是否被存储结构绑定 |
| M6  | **生命周期标准流程**：创建（工厂/构造）→ 变更（业务对象方法）→ 持久化（边界契约）→ 归档/删除                                                 | 审查：变更是否绕过业务对象方法   |
| M7  | **通过定义规避错误**：业务规则用语义覆盖边界情形（越界截断、删除不存在=成功），减少异常路径                                                  | 审查：领域逻辑异常分支数         |

#### 2.3.3 演进信号（出现任一 → 加深一级建模）

| 信号                                   | 加深到                          |
| -------------------------------------- | ------------------------------- |
| 业务对象需要身份区分（同属性不同对象） | 引入**实体**                    |
| 出现不可变的属性组合（金额/区间/状态） | 引入**值对象**                  |
| 多对象必须强一致同生共死（订单+明细）  | 引入**聚合**                    |
| 服务层堆积大量业务规则、逻辑无处安放   | 引入**领域服务** + 行为内聚改造 |
| 跨聚合/跨服务需要解耦协调、最终一致    | 引入**领域事件**                |
| 多团队/多系统术语冲突、模型互相污染    | 引入**限界上下文** + 上下文映射 |

#### 2.3.4 文档侧建模呈现（演进信号表）

> 文档建模与代码建模同步演进，**禁止超前建全套领域建模文档**（简单项目强上 = 反模式）。图件工具约定见 §3.2（图标准与工具约定）。

| 阶段                      | 建模复杂度       | 文档要求                                                  |
| ------------------------- | ---------------- | --------------------------------------------------------- |
| **阶段 0：简单数据管理**  | 无领域建模       | ER 图 + 数据字典 + 极简术语表                             |
| **阶段 1：业务规则复杂**  | 实体/值对象/聚合 | 领域模型图（概念+关系）+ 聚合边界说明                     |
| **阶段 2：多团队/多系统** | 限界上下文       | 限界上下文图 + **上下文映射图**（各上下文关系与集成模式） |
| **阶段 3：持续演进**      | 全量领域建模     | 事件风暴复盘 + 模型随代码迭代                             |

**文档一致性规则**：

| #   | 规范                                                                                                                                                                             | 检查方式                            |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| M8  | **图即文本**：文档图必须用文本化方式（D2 / Mermaid / ASCII 代码块，直接写入 .md），禁止位图截图/在线工具导出图——文本化才能进 Git、可 diff、可在任何渲染器显示（工具规范见 §3.2） | 检查：图是否以文本形式存在于 .md 内 |
| M9  | **通用语言贯穿**：文档术语 = 代码命名 = 画布词汇；术语表（GLOSSARY）与领域模型一致                                                                                               | 审查：术语是否三处一致              |
| M10 | **模型随代码演进**：重构代码必须同步更新领域模型图；模型失效就换模型，不硬撑                                                                                                     | 审查：代码变更是否同步图            |
| M11 | **建模构件按信号逐级引入**：按 2.3.3 演进信号表引入构件、按 2.3.4 阶段表引入文档——不跳级、不超前                                                                                 | 审查：建模深度与项目复杂度是否匹配  |

**通用规则**：

1. **工具分工**：**D2 只用于"容器式分层图"**（多层大容器嵌套）；**其他所有图用 Mermaid**（flowchart / stateDiagram / sequenceDiagram / erDiagram / mindmap / classDiagram）。Mermaid 在主流 Markdown 平台原生渲染；D2 需通过 `c4-container-diagram` 工具渲染。
2. **Fallback**：系统找不到对应工具/渲染环境时，一律退化为 **ASCII 图**（文本可 diff、任何环境显示），保持同样的结构/布局规范。
3. **结构图标注真实类型**：flowchart 可画结构/拓扑图（subgraph 分组），但图旁标注**必须写真实类型**（如"本图为上下文映射图/部署拓扑图"），不套用"流程图"标签。
4. **状态流转 vs 状态机**：流式线性状态片段（DOMAIN-MODEL §3 Action）用 flowchart；完整环式状态机（DOMAIN-MODEL §3.6）用 stateDiagram-v2，不混用。
5. **容器图特则**：多层大容器纵向嵌套、每层子容器显式算 width（等宽居中）、全圆角、按层配色、文字深色（对比度 ≥ 4.5:1）——细节见 `c4-container-diagram` 工具。
6. **文档标注**：各文档图旁只需标"本图是什么图"（如"本图为 C4 容器图"），绘制方式引用本节，不复制工具细节。
7. **能力图编码规范（状态线型 + 优先级热力 · 一眼可见）**：**产品能力架构图（PRODUCT §2.1）用节点线型表达实现状态、节点颜色表达投资优先级**——两个视觉通道叠加在节点上（`class: [module; planned; core]` 组合）。**编码规则（SSOT）**：
   - **线型 = 状态**：实线框（`stroke-width: 2`）= 已实现；虚线框（`stroke-dash: 4`）= 规划中/待实现（中间态如 POC 验证中也用虚线，细节在能力清单表标注）
   - **颜色 = 优先级热力**：红（`#dc2626`）= 核心（优先投资）；橙（`#f59e0b`）= 支撑（按需投入）；灰（`#d1d5db`）= 边缘（探索/低优先）
   - **入口层不设热力色**：页面/触点不是能力，无优先级维度（保持白底）
   - 图底部放**图例说明**（线型表 + 颜色表），读者一眼读懂状态与优先级
   - **归属**：状态与优先级是产品层信息，**唯一事实源在 PRODUCT §2（架构图 + 能力清单表）**，其他文档引用不复制；演进时状态/优先级变化只改 PRODUCT

### 3.3 代码分层（前端/后端分开，固定分层）

> 分层是**手段不是目的**：目标是依赖单向、关注点分离。**前端与后端是两套独立的分层体系**，采用**固定分层**（不再演进加层）——DDD 分层能覆盖大多数场景，避免为"规范/模板"反复加层。
>
> **依赖总则（前后端通用）**：
>
> - **单向依赖**：层间依赖只允许上层指向下层（依赖方向与调用方向一致）；下层禁止依赖上层
> - **松散分层**：允许上层依赖任意下方层（可跳层），不强制"只能依赖直接下层"（业界主流，避免简单项目痛苦）
> - **依赖倒置（DIP）**：出现"下层需要调用上层逻辑"的反向需求时，**不得打破单向依赖**——由上层定义接口、下层实现该接口，使依赖方向指向抽象而非具体层（Clean Architecture 规则）
> - **代码审查自检**：发现任何反向依赖（下层 import/引用上层）即为违规，用 DIP 重构
> - **目录命名统一小写**：分层目录一律小写（`controller/`、`service/`、`infra/`、`integration/`、`service/*/domain/`、`pages/`、`components/`、`store/`、`utils/`）

**前端固定 3 层**：

```
表现层（pages 页面 / components 组件）
   ↓ 只允许向下依赖
业务层（store 状态管理 / services 服务）
   ↓ 只允许向下依赖
基础设施层（utils 工具 / api 请求封装 / assets 静态资源）
```

**后端固定分层（DDD，顶层 4 个一级目录，全小写）**：

```
controller  接入层（接参/参数校验/响应封装/翻译 DTO→Domain）
   ↓ 只允许向下依赖
service     业务层（含 domain 横向层）
  ├─ service/   应用服务（编排用例/事务/权限/协调领域对象）
  └─ domain/    领域层（聚合根/实体/值对象/领域服务/仓储接口——横向层）
   ↑          ↑
infra     integration
支撑层-内部      支撑层-外部
```

> **domain 层是横向层**：在 `service/` 目录内，被 `service/service`（上方）与 `infra`/`integration`（下方）**同时依赖**，但 `domain` 自身不依赖任何层——它是依赖的汇聚点，只定义接口（依赖倒置的落点）。聚合/实体/值对象/领域服务都归 `service/*/domain/`。
>
> **infra 与 integration：顶层平级的一级目录（支撑层拆两个目录）**：两者**同属支撑层、平级、不是上下级**，都依赖 `service/domain`、互不包含。区别只在**管什么**：判断标准 = **资源归谁管**：
>
> | 目录                         | 管什么           | 谁维护           | 例子                                            |
> | ---------------------------- | ---------------- | ---------------- | ----------------------------------------------- |
> | **infra/**（基础设施）       | **内部资源**     | **自己**运维管理 | 数据库（DB）、缓存（Redis）、消息队列、文件存储 |
> | **integration/**（外部集成） | **外部系统对接** | **别人**提供服务 | 微信 API、支付宝支付、第三方 AI（DeepSeek/OCR） |
>
> **判断口诀**："这个东西坏了找谁修？"——找自己修（DB 挂了自行处理）→ `infra`；找别人修（微信挂了只能等）→ `integration`。两者都通过接口/适配器接入，都翻译成 Domain 模型（ACL 防腐层在 `integration/` 里）。

**层间纪律（前后端通用）**：

- 层间依赖单向向下，下层禁止依赖上层（反向需求用依赖倒置解决）
- **前端特有约束——单向数据流**：组件间数据流单向——父组件通过 props 下行传数据，子组件不得直接修改 props，只能通过事件（$emit/回调）上行请求父组件变更；**页面依赖组件，组件禁止依赖页面**（Vue/React 框架级约束）
- **后端特有约束**：业务规则内聚于 `domain/` 的领域对象（聚合根承载行为），`service` 只做编排不堆业务；跨聚合/跨上下文用领域事件解耦
