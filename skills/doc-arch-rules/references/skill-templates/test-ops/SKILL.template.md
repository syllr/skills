# test-ops — 测试用例全生命周期

AI 是测试执行器（契约驱动范式，见项目 ADR）：读 case 文档 → 按六关切骨架执行 → 数据落库对账定胜负。**工具只取证据，断言由 AI 核销**。

## 1. 职责

- **写用例**：从 openapi 契约生成（不是从实现猜）——读契约 responses/schema/领域规则，构造验证点，按六关切骨架落盘
- **跑用例**：读卡 → 按「怎么调」执行 → 按「断什么」核对 → 按「对什么账」取证据 → 逐条记录 pass/fail
- **更新用例**：openapi 契约变更（端点/字段/错误响应）→ 定位受影响 case → 联动更新 → 同步用例索引与 RTM

## 2. 工具箱

> 【实例化】本节按目标项目实际测试工具生成：探测 `<测试工具目录>/package.json` 的 scripts 与其 README，产出工具清单表（工具/干什么/关键参数）与环境变量清单（含 `.env` 约定）。下表为 enterprise-ai-hub 项目的实例基线。

| 工具                                                                  | 干什么                                                    | 关键参数                                                 |
| --------------------------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------- |
| `npm run api -- --operation <opId> --params '<JSON>' --body '<JSON>'` | 契约直调（swagger-client 运行时直读契约，拼错 fail-fast） | env：`API_BASE`/`API_TOKEN`；`--list` 列全部 operationId |
| `npm run webmcp -- --seq '[{"name":...,"args":{...}}]'`               | 前端 WebMCP 工具序列（同页面顺序执行，会话保持）          | `--headed` 人工旁观；`--list` 枚举已注册工具             |
| `npm run db -- --sql "<SQL>"`                                         | MySQL 只读对账（非 SELECT 强制拒绝）                      | env：`DB_*`                                              |
| `npm run ragflow -- datasets`                                         | RAGFlow 知识库/文档/chunks 对账                           | env：`RAGFLOW_*`                                         |

约定：stdout 单行 JSON；退出码 0=成功 / 1=断言失败 / 2=参数错 / 3=网络 / 4=DB / 10=配置。环境变量配在 `test-tools/.env`（不入库）。详见 `test-tools/README.md`。

## 3. 用例格式：六关切骨架（章节定义表）

每张 case 六个章节，职责固定不重叠；API 卡与 FLOW 卡同构，差异只在各关切的内容载体。**AI 先学会这张表，之后每张卡只读具体操作**：

| 章节                                  | 职责                        | API 卡载体                                                      | FLOW 卡载体                                                   |
| ------------------------------------- | --------------------------- | --------------------------------------------------------------- | ------------------------------------------------------------- |
| `## 测什么（关联 实体/Action/Event）` | 被测对象 + 验证点语义清单   | 实体/Action/Event 三元按实际填（查询类仅实体）+ 验证点 1…N 列表 | 同左 + **Gherkin 场景声明**（人类评审用）                     |
| `## 怎么调（入口与命令）`             | 唯一入口 + 各验证点具体请求 | 公共请求体 + 各验证点差异（缺字段=JSON 无该键）                 | `npm run webmcp -- --seq ...` 命令 + 页面表单形态字段说明     |
| `## 断什么（关键断言）`               | 每个验证点的期望（判据）    | 逐验证点 status + `$.code/字段`                                 | 旅程断言 + `toHaveScreenshot` 补充                            |
| `## 对什么账（数据落库对账）`         | 每个验证点的对账证据        | 逐验证点 SQL + 期望值                                           | 真实命令（api/ragflow/db）+ 期望                              |
| `## 怎么跑（执行流程）`               | AI 编排顺序                 | 前置→按验证点执行→核对→清理                                     | **mermaid 时序图**（四段：前置蓝/被测绿/异步橙/对账红）+ 步骤 |
| `## 环境卫生`                         | 数据标识与清理              | `TEST-` 前缀标识 + 清理方式                                     | 同左                                                          |

规则：章节职责单一不重叠（验证点语义只在测什么、请求只在怎么调、判据只在断什么、SQL 只在对什么账）；验证点序号（验证点 1…N）是跨段对齐键；唯一入口（入口失败 = bug 报错，无主备降级）。

## 4. 断言三源纪律

验证点的断言信息按此分层取，不得臆造：

1. **状态码**：只从 openapi operation 的 `responses` 定义取——契约没有的码不许出现在 case 里
2. **响应字段**：`body_path` 的字段名从响应 schema 取（错误响应 = `ErrorResponse{code, message, details}`，code 为 UPPER_SNAKE）
3. **具体错误码值**：schema 为 free string 不含全量枚举——以**实测校准**（模式：字段级校验 = `BAD_REQUEST`，规则级 = `RULE_VIOLATION_R<N>`，N 对应 domain 规则编号）

实测与契约不符时：以契约为准修实现或以实现为准修契约（项目差异分诊规则），漂移记项目漂移清单；**case 断言跟随裁决结果，不迁就任何一方的错误**。

## 5. 执行纪律

- **顺序**：先跑 case「怎么跑」的前置（登录 → token 注入）→ 逐验证点执行 → 每条核对「断什么」→ 执行「对什么账」→ 「环境卫生」清理
- **实测校准优先**：case 断言与实际响应不符 = 立即停下查契约（三源），确认是实现 bug 报给用户、是 case 错就修 case、是契约漂移记漂移清单——不静默改断言凑通过
- **真实调用**：所有验证点真实执行（不是 mock 推演）；写入类操作用项目约定前缀标识，跑完清理
- **对账是最终判据**：接口 200 ≠ 功能正确，落库/知识库证据齐才算通过

## 6. 流程

**写用例**：读契约（对应 operation 的 responses + 请求 schema）→ 读 domain 文档（关联 Action/Event/规则编号）→ 构造验证点（正路径 + 负路径 + 边界，参考数据落库验证矩阵）→ 六关切落盘用例目录 → 同步用例索引与 RTM

**跑用例**：读卡 → 按「怎么跑」执行 → 输出逐验证点 pass/fail + 对账证据 → 失败项按断言三源定位（实现 bug / case 错 / 契约漂移）→ 汇报

**更新用例**：openapi 端点/字段/错误响应变更 → grep 定位受影响 case → 更新验证点与断言（重新走断言三源）→ 同步索引
