# docs-align — 文档对齐与漂移处理

定位：项目差异分诊（宪法 §2.2 第 5 条）的执行器——以代码为准修复/生成文档，全程遵守对应 rule（等价于按 rule 重新生成受影响部分）。`.omo/drift/` 漂移清单由分诊 1（对齐）产出、分诊 2（解决漂移）消费并清账；分诊 3（初始化）在 `docs/` 缺失时按 rule 从代码建文档。

前置：项目已由 doc-arch-rules 生成 rule（`.omo/rules/docs/`）——rule 的 globs 是文档清单与扫描范围的依据；未生成时先跑 doc-arch-rules 的生成 rule 流程。

## 1. 功能分诊（进入第一件事）

| 分诊结果     | 触发                                                                                                                                                                        | 动作                                                                                                                       |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 1 扫描检测   | 诊断类请求：「检查文档和代码有没有漂移」「扫描漂移」「看看有没有漂移」；「更新globs」「globs对齐」「目录变动」「rule没触发」= globs 轻量                                     | 走 §2：扫描检测 = 阶段 1-4 + 阶段 5 落漂移清单（只诊断记录，不询问不修复）；globs 轻量 = 仅阶段 1-2（提案交用户确认后写 frontmatter） |
| 2 处置漂移   | 「解决漂移」「处理漂移清单」「以代码为准修文档」「docs 和代码对齐」，或 `.omo/drift/` 已有清单且用户要求处理                                                                  | 走 §3：消费清单 → 逐条问用户决断 → 修复 → 清账（唯一询问用户处）                                                            |
| 3 文档初始化 | 「生成文档」「初始化文档」「按rule建文档」，或默认扫描检出 `docs/` 缺失且用户要求初始化                                                                                       | 走 §4：补 `docs/` 缺口（已存在不重建），按 rule 以代码为准生成，决策类与用户访谈                                            |

## 2. 扫描检测（诊断流程：盘点 → globs 自适应 → 机检 → 语义核对 → 落清单）

执行范围由分诊裁剪：扫描检测 = 阶段 1-5；globs 轻量（「更新globs」等关键字触发）= 阶段 1-2。

### 阶段 1 · 盘点（全量扫描，不抽样）

① 全仓目录漫游：`ls -R`（排除 `.git/node_modules/dist/build/.venv/__pycache__`），产出实际目录树 + 各顶层目录文件数；② 读 `.omo/rules/docs/` 全部 rule 的 globs 得文档清单；③ 以实际目录树为准判定每个目录"干什么"（STRUCTURE §2 只做职责解释，现状以 `ls` 为准），STRUCTURE 文档与实际不一致即记漂移；④ 每份文档标注机检点（阶段 3 表）+ 其代码扫描范围（阶段 2 映射）。

输出必须含「实际顶层目录清单 + 文件数」，缺此即未完成，不得进入阶段 3。

### 阶段 2 · globs 自适应（按目录现状扩展 globs）

先读 rule 的 globs 语法说明，再读 `docs/common/STRUCTURE.md` §1 目录树（无该文档则以 `ls` 现状为准）+ `ls` 实际目录，逐目录判定"它是干什么的"（职责见 STRUCTURE §2；任何目录都算，不限代码——纯文档目录/资源目录同样进入映射），产出目录与文档的映射（目录/文件模式对应 rule）；再逐 rule 对账「基线 globs + 已有扩展」与目录现状，产出双向同步提案——追加/清理/改名成对/基线永不清理/合并保留为流程不变量；提案交用户确认，确认后写 rule frontmatter `globs` 并复核基线子集通过。

本阶段为必做门槛：无论目录是否变动都必须执行并给出显式结论——输出三件套：① 目录变动结论（`ls` 实际与 STRUCTURE §1 对比，无变动也要写明）；② 逐 rule globs 对账表（缺口 = 待追加，死条目 = 待清理）；③ 双向同步提案（追加 + 清理）或"无需变更"结论。三者缺一即未完成；禁止静默跳过。

### 阶段 3 · 机检（grep/ls/diff 按清单执行）

| 机检点                                                                                        | 方法                                                                                 |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 文档内 File:Line 引用有效性                                                                   | 文件存在 + grep 符号存在                                                             |
| STRUCTURE 目录树与实际目录对比                                                                | diff 目录树与 `ls -R`                                                                |
| openapi.yaml 尾注释计数 vs API.md §1 端点计数列 vs 代码路由数                                 | 三方计数对比                                                                         |
| 交叉引用死链（文档 A 引 文档 B §X，B 无该节）                                                 | grep 目标文档章节标题                                                                |
| 实例头部原则块/建模方法论残留（「> 【原则】」「决策速查」「领域事件原则」「Q1-Q6」）          | `grep -rnE -e '^> 【原则】' -e '决策速查' -e '领域事件原则' -e 'Q1-Q6' docs/` 应为 0 |
| 目录归属口诀例外（STRUCTURE infra/integration 归属判别口诀属合法读者内容，不进全 docs/ 检查） | 建模方法论口诀只在域文档禁：docs/L2/domain/ 下域文档另查对象类型判据/判断口诀应为 0  |
| PRODUCT 能力行与 DOMAIN Action 清单双向对齐                                                   | 交叉 grep 能力名/Action 名                                                           |
| DOMAIN 方法签名 vs 代码函数签名                                                               | grep `def`/`func` 匹配 §3 领域操作方法详情竖表「方法签名」行                         |

### 阶段 4 · AI 语义核对（逐文档全读，不抽样）

对每份文档，按其 rule globs（含阶段 2 扩展）列出本次已读代码文件清单，逐文件读后对照文档陈述（行为/规则/流程/约束），差异逐条记「文件:位置 / 文档陈述 vs 代码事实」。

禁止抽样（只读 1-2 个代表文件即违规），禁止无 File:Line 佐证的"一致/无漂移"结论；输出必须含每文档「已读 N 个文件」+ 文件清单，否则视为没读。

### 阶段 5 · 落清单（扫描产出，不询问不修复）

把阶段 3 机检 + 阶段 4 语义核对检出的差异逐条落成 `.omo/drift/<doc>.md`（格式见 §5）：每条记 位置 / 差异（文档 vs 代码，含 File:Line）/ 漂移原因（AI 判断，如代码重构未同步 / 需求变更 / 实现简化 / 契约理想与实现差距）/ 状态=待修复；用户决断留空——扫描阶段只记录不询问，裁决在分诊 2 处置时发生。

输出：漂移清单 + globs 对账三件套 + 每文档已读文件清单。

## 3. 处置漂移（消费 .omo/drift/ 清单——唯一询问用户处）

1. 读清单：`ls .omo/drift/`；无清单时告知当前无待处理漂移（建议先走分诊 1 扫描产出），结束
2. 逐条分析：按清单「位置 / 差异」重读代码与文档对应位置，校准性质（实现 bug / 文档错 / 契约漂移）、漂移原因与定级（严重：影响 API 契约/用户故事验收；轻微）
3. 问用户决断（唯一询问处）：逐条交用户裁决——以文档为准（改代码，需用户二次确认）/ 以代码为准（改文档）/ 逐条判断；裁决写入「用户决断」列
4. 执行处置：按决断修——文档按对应 rule 重新生成受影响节，修后跑该 rule checks 验证；实现 bug 只报告不动代码
5. 清账：每修一条立即更新清单状态（已修复）；单文件全部「已修复」后 `rm` 该清单文件（空目录一并删除），完成判定叠加已删章节 §x 零残留

## 4. 文档初始化（docs/ 缺失或残缺，按 rule 生成）

适用：项目有 `.omo/rules/docs/` 但 `docs/` 缺失或残缺，用户要求「生成文档」「初始化文档」「按 rule 建文档」；或默认对齐检出 `docs/` 缺失时先问用户是否初始化。

1. 缺口盘点：逐 rule 按 globs 列目标文档，判定 存在/缺失/空壳；已存在的归分诊 1 对齐（不重建、不覆盖），只补缺口；缺口清单（文档 / 现状 / 建议）交用户确认生成范围
2. 信息源定级：逐份标注来源——代码派生（L2 架构 / L3 契约 / L4 交付 / common，扫描代码库得出）或 用户访谈（L1 产品目标与用户故事，代码推不出）；代码不足以支撑的按访谈处理
3. 顺序铁律（硬约束，见宪法 §3.1 生成顺序）：严格自上而下逐层串行——宪法（CONSTITUTION，基线，不生成 docs 副本）先，然后 L1、L2、L3、L4，common 最后（贯穿层需综合各层结论）；每层全部文档生成并经用户确认后才进下一层，禁止跳层、乱序、并行（如先 L2 后 L1）。列「文档 / 信息源 / 顺序」清单交用户确认后动手
4. 逐份生成：生成某层文档前，先读宪法 + 上一层已落盘文档作为输入（下层结论须与上层对齐），再读对应 rule 的生成要求——代码派生类扫描代码、访谈类与用户逐条谈定要点——写 `docs/<路径>`，跑该 rule checks 验证；谈定一份写一份，不积压、不跳层
5. 收尾：globs 自适应复核（初始化新增目录对应 rule globs 扩展）+ 报告（生成清单 / 每份信息源 / 待用户补充项）

## 5. 漂移清单格式（.omo/drift/，扫描产出、处置消费）

发现 code-doc 漂移时按漂移文件各落一清单 `.omo/drift/<doc>.md`（如 `docs/L2/DATA-ARCHITECTURE.md` 的漂移对应 `.omo/drift/DATA-ARCHITECTURE.md`）：

一份清单只承载一个文档的漂移项；一个文件内只有一张表（清单即待办列表）：

- 表头固定六列：`#` / 位置 / 差异（文档 vs 代码）/ 漂移原因 / 用户决断 / 状态（竖线须转义）
- 漂移原因：扫描阶段由 AI 判断记录（代码重构未同步 / 需求变更 / 实现简化 / 契约理想与实现差距等）
- 用户决断：扫描阶段留空（`—`）；处置阶段由用户裁决填入（以文档为准 / 以代码为准 / 逐条）
- 状态枚举仅两态：`待修复`（默认，发现即记）/ `已修复`（修完标记）；符号 `☐`/`☑` 可选前缀——全部已修复即 `rm` 清单文件（空目录一并删除）
- 扫描阶段只记录不询问；处置阶段才问用户决断并回写；每修一条立即更新状态
- 清单在跟踪期入库（团队可见）；完成判定叠加：`grep -rn "§x" docs/ .omo/rules/` 对已删章节零残留

模板：

```markdown
# drift · <doc>

| #   | 位置          | 差异（文档 vs 代码）                              | 漂移原因        | 用户决断   | 状态     |
| --- | ------------- | ------------------------------------------------- | --------------- | ---------- | -------- |
| 1   | §X.Y <章节名> | 文档："<文档陈述>"；代码：<代码事实（File:Line）> | <AI 判断的原因> | —          | ☐ 待修复 |
| 2   | §X.Z <章节名> | 文档："<文档陈述>"；代码：<代码事实（File:Line）> | <原因>          | 以代码为准 | ☑ 已修复 |
```

## 6. 输出与边界

输出报告：漂移清单（文件:位置 / 差异 / 判定：漂移或疑似 bug / 处置：已修或待用户裁决）+ globs 对账三件套 + 每文档已读文件清单。

边界：只检测、修复与初始化 `docs/**` 文档（rule 覆盖范围）；不修代码（疑似 bug 交用户裁决）；不自动 commit/push；`.omo/evidence` 属历史记录不追溯。
