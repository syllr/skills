# docs-align — 文档-代码漂移检测与修复

定位：项目差异分诊（宪法 §2.2 第 5 条）的执行器——以代码为准修复文档，修复时遵守对应 rule（等价于按 rule 重新生成受影响部分）。

前置：项目已由 doc-arch-rules 生成 rule（`.omo/rules/docs/`）——rule 的 globs 是文档清单与扫描范围的依据；未生成时先跑 doc-arch-rules 的生成 rule 流程。

## 1. 触发与模式

| 模式       | 触发                                                 | 动作                                                |
| ---------- | ---------------------------------------------------- | --------------------------------------------------- |
| 只读机检   | 「检查文档和代码有没有漂移」（疑问）                 | 阶段 1-3 只读执行，输出报告不写文件                 |
| 对齐修复   | 「以代码为准修文档」「docs 和代码对齐」（命令）      | 五阶段全量，按分诊结论动手                          |
| globs 轻量 | 「更新globs」「globs对齐」「目录变动」「rule没触发」 | 只跑阶段 1 盘点 + 阶段 2 globs 自适应，跳过阶段 3-5 |

## 2. 五阶段流程

### 阶段 1 · 盘点（全量扫描，不抽样）

① 全仓目录漫游：`ls -R`（排除 `.git/node_modules/dist/build/.venv/__pycache__`），产出实际目录树 + 各顶层目录文件数；② 读 `.omo/rules/docs/` 全部 rule 的 globs → 文档清单；③ 以实际目录树为准判定每个目录"干什么"（STRUCTURE §2 只做职责解释，现状以 `ls` 为准），STRUCTURE 文档与实际不一致即记漂移；④ 每份文档标注机检点（阶段 3 表）+ 其代码扫描范围（阶段 2 映射）。

**输出必须含「实际顶层目录清单 + 文件数」**，缺此即未完成，不得进入阶段 3。

### 阶段 2 · globs 自适应（目录现状 → globs 扩展）

先读 rule 的 globs 语法说明，再读 `docs/common/STRUCTURE.md` §1 目录树（无该文档则以 `ls` 现状为准）+ `ls` 实际目录，逐目录判定"它是干什么的"（职责见 STRUCTURE §2；任何目录都算，不限代码——纯文档目录/资源目录同样进入映射），产出目录→文档映射（目录/文件模式 → 对应 rule）；再逐 rule 对账「基线 globs + 已有扩展」vs 目录现状，产出双向同步提案——**追加/清理/改名成对/基线永不清理/合并保留**为流程不变量；提案交用户确认，确认后写 rule frontmatter `globs` 并复核基线子集通过。

**本阶段为必做门槛**：无论目录是否变动都必须执行并给出显式结论——输出三件套：① 目录变动结论（`ls` 实际 vs STRUCTURE §1，无变动也要写明）；② 逐 rule globs 对账表（缺口 = 待追加，死条目 = 待清理）；③ 双向同步提案（追加 + 清理）或"无需变更"结论。三者缺一即未完成；禁止静默跳过。

### 阶段 3 · 机检（grep/ls/diff 按清单执行）

| 机检点                                                                                        | 方法                                                                                 |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 文档内 File:Line 引用有效性                                                                   | 文件存在 + grep 符号存在                                                             |
| STRUCTURE 目录树 vs 实际目录                                                                  | diff 目录树与 `ls -R`                                                                |
| openapi.yaml 尾注释计数 vs API.md §1 端点计数列 vs 代码路由数                                 | 三方计数对比                                                                         |
| 交叉引用死链（文档 A 引 文档 B §X，B 无该节）                                                 | grep 目标文档章节标题                                                                |
| 实例头部原则块/建模方法论残留（「> 【原则】」「决策速查」「领域事件原则」「Q1-Q6」）          | `grep -rnE -e '^> 【原则】' -e '决策速查' -e '领域事件原则' -e 'Q1-Q6' docs/` 应为 0 |
| 目录归属口诀例外（STRUCTURE infra/integration 归属判别口诀属合法读者内容，不进全 docs/ 检查） | 建模方法论口诀只在域文档禁：docs/L2/domain/ 下域文档另查对象类型判据/判断口诀应为 0  |
| PRODUCT 能力行 ↔ DOMAIN Action 清单双向对齐                                                   | 交叉 grep 能力名/Action 名                                                           |
| DOMAIN 方法签名 vs 代码函数签名                                                               | grep `def`/`func` 匹配 §3 领域操作方法详情竖表「方法签名」行                         |

### 阶段 4 · AI 语义核对（逐文档全读，不抽样）

对每份文档，按其 rule globs（含阶段 2 扩展）列出本次已读代码文件清单，逐文件读后对照文档陈述（行为/规则/流程/约束），差异逐条记「文件:位置 / 文档陈述 vs 代码事实」。

**禁止抽样**（只读 1-2 个代表文件即违规），**禁止无 File:Line 佐证的"一致/无漂移"结论**；输出必须含每文档「已读 N 个文件」+ 文件清单，否则视为没读。

### 阶段 5 · 分诊修复（严格走四步分诊，按序执行）

- ① **先判是否为 Bug**：代码偏离文档真实意图（文档真实反映用户需求，代码写错）→ 停下问用户裁决：用户认可才修代码；不认可则按文档为准改文档；非 Bug 才走 ②③④
- ② **自动化优先**：机检可判定的先自动处理；无自动化工具时跳过
- ③ **默认以代码为准修文档**：按对应 rule 重新生成受影响节，修后跑该 rule 的 checks 验证
- ④ **漂移定级**：严重（影响 API 契约/用户故事验收）/ 轻微——严重优先修、轻微顺手修

## 3. 漂移清单（.omo/drift/）

发现 code-doc 漂移时，**按漂移文件**各落一清单 `.omo/drift/<doc>.md`（如 `docs/L2/DATA-ARCHITECTURE.md` 的漂移 → `.omo/drift/DATA-ARCHITECTURE.md`），机制与格式：

- **默认记录不问处置**（发现即记，处置在阶段 5 分诊时定）
- 表头固定四列：`#` / 位置 / 差异（文档 vs 代码）/ 状态（竖线须转义）；状态枚举 `待修复/修复中/已修复/已验证`（☐/◐/☑ 可选前缀）
- 真正修复时增补「建议/判定」列（建议 = 预判以文档/以代码，判定 = 用户逐条裁决）；每修一条立即更新状态
- 标题行：`## Drift: <doc>（YYYY-MM-DD HH:mm 生成，来源：rule 指纹 + 代码漂移）`
- 单文件全部「已验证」后立即 `rm` 该 drift 文件（空目录一并删除），禁止入库
- 完成判定叠加：`grep -rn "§x" docs/ .omo/rules/` 对已删章节零残留

## 4. 输出与边界

**输出报告**：漂移清单（文件:位置 / 差异 / 判定：漂移或疑似 Bug / 处置：已修或待用户裁决）+ globs 对账三件套 + 每文档已读文件清单。

**边界**：只检测与修复 `docs/**` 文档（rule 覆盖范围）；不修代码（疑似 Bug 交用户裁决）；不自动 commit/push；`.omo/plans` 与 `.omo/evidence` 属历史记录不追溯。
