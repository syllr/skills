# 测试工具集架构规范（test-tools 模板）

test-tools 是 AI 测试执行的基础设施（一个小型测试项目）——测试用例的所有操作必须经它执行。本文档定义其架构、工具分类与生成原则；项目落地时按此架构实例化，后续新工具一律按本文档生成。

## 1. 定位与边界（为什么是"小测试项目"）

- 唯一执行入口：测试用例（docs/test/test-cases/）的所有操作只能经 test-tools 执行——不允许绕过（不写 curl、不裸 SQL、不用其它通道直连被测系统）
- 用例必须调工具：case 命令 = 工具调用；工具是 AI 测试执行器与被测系统之间的唯一连接层
- 工具只取证据/执行操作，断言由 AI 判断：工具不内置断言逻辑
- 自身可独立演进（工具是代码资产，有依赖/版本/测试），故按小型项目管理

## 2. 工具分类架构

工具按职责分三类，前两类通用（被测系统有前端/有后端契约即必有），第三类按项目定制（随被测系统数据落位扩展）：

| 类 | 工具示例 | 通用性 | 宿主/通道 | 用途 |
| --- | --- | --- | --- | --- |
| ① 模拟用户操作（前端） | WebMCP 类（页面注册业务能力工具） | 通用（有前端必有） | 浏览器（驱动页面内注册工具） | 被测操作走页面流程（表单校验/组装等价人工） |
| ② 后端契约直调 | API 类（HTTP 契约，operationId 驱动） | 通用（有后端契约必有） | bash（HTTP） | 契约直调被测后端接口 |
| ③ 校验/对账（按数据落位） | DB 类（业务库只读对账）、向量库/对象存储/缓存/消息 类 | 定制（每个项目按被测系统真实落位扩展） | bash | 操作后到真实数据落位处取证据 |

> ①②每项目必有；③随项目增长——被测系统引入 Redis/Kafka/新存储/新中间件时，新增对应校验工具。

## 3. 工具形态统一契约（所有工具一致）

| 契约项 | 约定 |
| --- | --- |
| stdout | 只输出一行 JSON（AI 据此判断；人类诊断走 stderr） |
| 退出码 | 0=成功 / 1=执行成功但断言/对账失败 / 2=参数错 / 3=网络 / 4=数据层 / 10=配置错 |
| 环境变量 | 连接参数经 `.env`（不入库）；命令行注入优先于 .env |
| host | 一律走 `.env`（如 WEBMCP_URL/API_BASE/DB_HOST），工具与文档不写死 host |
| --help | 每工具必带用法 |
| fail-fast 契约校验 | 输入键必须 ∈ 被测契约声明（契约外的键发送前报错并提示可用清单） |
| 只读红线 | 校验/对账类只放行只读操作（非只读语句拒绝） |
| 可控清理 | 数据清理提供受控入口（按测试标识级联删 + 事务回滚），不开放任意写 |
| 无裸系统命令 | 工具内部统一走语言 HTTP 客户端/驱动库，不依赖 curl 等外部命令 |
| 契约源运行时适配 | 契约（如 openapi）变更 → 工具读契约运行时适配（自动 bundle/重解析），不硬编码端点清单 |
| 确定性 | 同输入同输出；文件/时间相关输入用参数注入 |

## 4. 命令形态原则

- 参数名只在需要选择/歧义时存在：工具唯一职能的操作直接裸传主体（对账工具直接收 SQL 语句，不加 `--sql` 包装）；需选择目标才带选择参数（契约直调用 `--operation <operationId>` 选接口）
- 通道显式：有 URL/body 多通道时按通道拆参数（`--path/--query/--header/--body`），不做自动归位的隐晦分拣
- 工具语法解释归工具 README——不写入用例卡（卡内只放命令）

## 5. 生成原则（AI 新增工具时的行为规范）

遇新工具需求（被测系统引入 Redis/Kafka/新存储/新中间件，或新前端/新契约域）：

1. 分类归属判断：新工具是操作类还是校验类？——模拟用户操作/契约直调 → 参考 ①② 类既有工具；数据校验对账 → 参考 ③ 类既有工具（如 DB 工具）
2. 参考模板与既有同类生成，不现想：以本架构 + `docs/test/test-tools/` 下既有同类工具为样板扩展新 `tools/<name>.mjs`；不要重新设计架构、不要照搬外部项目
3. 遵守统一契约（§3）+ 命令形态（§4）
4. 配套登记：README 工具清单表 + `package.json` scripts 别名 + `.env.example`（新连接参数）
5. 工具语法/参数在工具 README 说明（不落用例卡）

## 6. 目录结构与维护

```
docs/test/test-tools/
├── tools/                    # 工具实现（Node .mjs：跨平台零编译）
│   ├── webmcp.mjs            # ① 前端工具（浏览器驱动，统一入口）
│   ├── api.mjs               # ② 后端契约直调
│   ├── db.mjs                # ③ 校验类样板（业务库只读对账）
│   ├── ragflow.mjs           # ③ 校验类（中间件对账，按项目）
│   ├── ...（新工具按 §5 生成）
│   └── _util.mjs             # 共享：JSON 输出/退出码/env/参数解析
├── .env（不入库）· .env.example
└── README.md（工具清单/用法/退出码/环境变量）
```

- 分发 = 拷贝目录 + 一次依赖安装（无编译产物）
- 环境 host 变更只改 `.env`（工具与用例卡不感知）

## 7. 参考实现（完整工具集模板）

同目录 `test-tools/` 为完整参考实现（Node .mjs：api/db/webmcp/ragflow/_util + package.json + README + .env.example）——生成/扩展工具时以它为样板：复制到目标项目 `docs/test/test-tools/`，按被测系统替换 `.env` 值；新增校验类工具参照 db.mjs/ragflow.mjs 的只读+清理模式扩展。契约源路径（如 docs/L3/openapi）为 doc-arch 通用结构，随项目沿用。
