# test-template 模板资产使用说明

本目录（含 `test-tools/` 参考实现）的全部内容本质都是模板——生成/编写测试资产（工具、用例卡）时参考这里的模式与契约来写，不是拿来即用的成品、也不是唯一实现。参考 = 看结构、照契约、按被测系统实况写。

## 资产清单

| 资产            | 是什么               | 怎么用                                                                                                  |
| --------------- | -------------------- | ------------------------------------------------------------------------------------------------------- |
| `api-case.md`   | API 用例卡模板       | 生成 API 卡：复制结构（头 + Case N 五段）→ 替换接口/实体/Case 内容 → 落到 `test/test-cases/api/<实体>/` |
| `flow-case.md`  | FLOW 用例卡模板      | 生成 FLOW 卡：复制结构 → 按 USER-STORY 场景填充 → 落 `flow/<场景>/`                                     |
| `test-tools.md` | 测试工具架构规范     | 工具集整体架构/分类/契约/纪律基准——写任何工具前先读                                                     |
| `test-tools/`   | 测试工具完整参考实现 | 写新工具/改工具时的代码级样板——看其模式照写，含项目特定值处按被测系统替换                               |

## test-tools 参考实现的使用规则

`test-tools/` 下的每个 `.mjs`/配置都是从实际项目提炼的参考实现，本质是模式样板：

- 写新工具时参考其实现模式（统一契约：stdout 单行 JSON/退出码/env/.env/fail-fast 契约校验/只读红线/可控清理/--help），按被测系统实况写新实现
- 不要直接复制文件当成品用（内含项目特定值：示例编码/种子账号/连接参数样例——`tools/` 内连接一律走 .env，工具文件本身保持通用）
- 同一职责的工具只保留一个实现（以 test/test-tools/ 实际为准），模板供参考不参与运行

## 何时新增工具、何时修改既有工具

判定依据：职责边界——新职责域建新工具；同职责域演进改既有工具。

| 场景                                                                      | 动作                                                                                | 理由                                   |
| ------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------- |
| 被测系统引入新的数据/中间件落位（Redis/Kafka/新存储/新库/新向量服务） | 新增 `tools/<name>.mjs`（校验/对账类，参照 db.mjs/ragflow.mjs 的只读+清理模式） | 新职责域——既有校验工具覆盖不到该数据源 |
| 被测系统新增前端页面能力域（新业务模块的 WebMCP 工具）                | 扩展既有前端工具（webmcp.mjs）或域文件——不是新增 CLI                            | 同一前端工具序列职责内扩展             |
| 被测系统后端契约变化（端点/字段/错误响应）                            | 修改既有 api.mjs（运行时适配契约）                                              | api 工具职责 = 契约直调，契约变了改它  |
| 既有工具的能力增强/缺陷修复（新参数/新子命令/对账新查询）             | 修改对应工具                                                                    | 同职责演进                             |
| 新增查询/操作模式但仍是既有工具的数据域                               | 修改既有工具（加子命令/参数）                                                   | 不扩大工具数量                         |

判断口诀：一个工具 = 一个职责域（前端操作 / 后端契约 / 某数据落位校验）。新职责域 → 新增；域内演进 → 修改。新增后登记（README 工具清单 + package.json scripts 别名 + .env.example）。
