## 1. 最高原则（唯一最终目的）

> 宪法的 **最终目的只有一个：降低系统复杂度**。所有其他原则、规范都是为实现这个目的的手段。

### 1.1 复杂度的定义

> 复杂度 = 让系统难以理解和修改的任何事物。它来自两个根源： **模糊性**与 **依赖性**（详见 1.2 / 1.3）。

**复杂度症状**（用于识别系统是否复杂）：① 改一处需连带改多处（变更放大）；② 理解某个模块需先学习大量背景（认知负荷高）；③
找不到关键信息的入口（信息缺失/不可达）。任一症状出现即存在复杂度，按 §2 手段处理。

**复杂度来源（分析纪律）**：复杂度按 **来源**分两类， **讨论/设计任何问题前先判断复杂度来自哪里**——两者处理手段完全不同，混淆会选错方案：

| 来源           | 是什么                       | 例子                                             | 处理方向                     |
| -------------- | ---------------------------- | ------------------------------------------------ | ---------------------------- |
| **技术复杂度** | 性能、并发、可用性等工程挑战 | 高并发、缓存、限流、吞吐                         | 技术手段（框架/中间件/架构） |
| **业务复杂度** | 需求纠缠、规则复杂、概念混乱 | <业务规则_入账扣减>必须记流水、<不变量_余额非负> | DDD 领域建模                 |

> 判断基准：这个问题 **难在技术**（工程挑战）还是 **难在业务**
> （规则/概念纠缠）？技术复杂多用工程手段，业务复杂多用领域建模。两者正交（一个系统可同时有两类复杂度），逐项分析避免一刀切。

### 1.2 模糊性

> **定义**：重要信息不明显、难以获取——需要知道某事，但找不到途径获知，甚至不知道存在问题。

| 维度     | 说明                                                                   |
| -------- | ---------------------------------------------------------------------- |
| 本质     | 信息缺失或难以获取，知识隐藏在代码/文档之外                            |
| 症状     | 认知负荷（需要大量学习才能动手）、未知的未知（不知道该改什么）         |
| 来源     | 命名歧义、注释缺失、文档不足、信息重复漂移、异常路径隐式、设计意图丢失 |
| 消除手段 | §2 引言分类 A：SSOT（§2.2）                                            |

**例子**：一个变量叫 `count` 却不知单位是"秒"还是"次"；一个接口不写注释，调用者必须读实现才能用——都是模糊性。

### 1.3 依赖性

> **定义**：代码无法孤立地理解和修改——改一处必须连带考虑/修改多处。

| 维度     | 说明                                                              |
| -------- | ----------------------------------------------------------------- |
| 本质     | 模块/对象之间存在隐式或强耦合，无法单独理解                       |
| 症状     | 变更放大（小改动需改多处）、认知负荷                              |
| 来源     | 模块间直接引用、跨层依赖、透传、接口耦合、隐式共享状态            |
| 消除手段 | §2 引言分类 B：模块设计（§2.1）、领域建模（见 DOMAIN-MODEL rule 方法论）、分层约束（见 STRUCTURE §3.1） |

**例子**：网站背景色在每个页面写死，改色需改所有页面；<实体_订单>对象直接持有另一聚合的对象引用——都是依赖性。

### 1.4 复杂度底线（价值观声明）

> 与最高目的直接相关的 **不可违反底线**（价值观声明，非可检查条款）：单次依赖/模糊项也必须处理，复杂性增量堆积须持续控制。具体执行见
> S4（差异主动修复）。

### 1.5 设计原则：架构与代码共同演进（Co-Evolution）

> **架构与代码共同演进、双向驱动**——架构设计指导代码，代码实现反哺架构， **无先后之分**
> 。让架构随每次迭代自动演进，避免"设计先行、纸上谈兵"。
>
> **闭环（双向）**：
>
> 1. **架构指导代码**：按当前架构原则（分层单向依赖、上下文分目录）编写代码
> 2. **代码反哺架构**：实现中发现架构不再匹配 → 调整架构（上下文重划、模式修正）
> 3. **对照模式审视**：用 DDD 战略/战术模式（9 种上下文映射、聚合边界）审视代码与架构，找出偏移点（该加 ACL 的、该拆聚合的）
> 4. **沉淀**：把演进后的架构沉淀到 DOMAIN-MODEL（领域建模）/ ADR（决策）；发现新原则再回写宪法
>
> **迭代收敛偏移（核心）**：每次迭代做两件事——
>
> - **收敛老偏移**：排查并修复已有功能中"架构与代码漂移"处（对齐，不让老的偏移累积）
> - **抑制新偏移**：新功能尽量少引入偏移（写前对照架构原则，写完审视）
>
> **长期保证**：只要每次迭代都收敛老偏移、并尽量减少新偏移，整体就能 **持续收敛、最终不偏移**——演进方向始终对齐架构。
>
> **建模优化信号（何时触发重划边界）**：审视代码时，以下信号 = **领域建模/边界划分有偏移**，触发「战略重划子域/上下文」：
>
> - **跨上下文传很多信息**（传递字段过多、参数列表冗长）——阈值示例：跨上下文传参 >5 字段或连续 3 个迭代都需补查即命中
> - **跨上下文需额外查询**（拿到 ID 后还要去 Infra/Integration 补查）
> - **跨上下文强耦合**（频繁互相 import、改一处连带改多处）
>
> **处理原则**： **战术上**先临时处理（传多字段 / 先查一次，跑通即可，记 drift 清单 `.omo/drift/`）； **战略上**
> 重新划分子域/限界上下文根治（这是建模偏移，不是代码问题）。具体 DDD 手段与演进决策记 ADR。
>
> **关键**：上下文关系（SK 共享 / C-S 上下游 / ACL 防腐）是 **架构与代码共同演进的自然结果**，不是编码前的蓝图——双向驱动、迭代对齐。具体分析流程记
> ADR。

## 2. 设计规范（手段的唯一表达地）

> **手段与目的**：宪法中「降低复杂度」的手段（§1 最高原则）分布在 **§2-§3**。按消除对象分两类组织：
>
> - **A 消除模糊性**（让信息明显、知识可获取）：单一事实源 SSOT（§2.2）
> - **B 降低依赖性**（让代码可孤立理解和修改）：模块设计（§2.1）、领域建模（见 DOMAIN-MODEL rule）、分层约束（见 STRUCTURE §3.1）
>
> 每条规范后标注【检查方式】，用于代码审查/AI 自检时验证。

### 2.1 架构的两个维度（同层解耦 + 跨层分层）

> **系统是立体的**：一个项目/系统要描述清楚，必须从两个方向组织—— **横向**（同一层内，业务与业务之间如何解耦）和 **纵向**
> （层与层之间如何组织）。

| 方向                 | 回答什么问题                             | 怎么做                                               | 对应章节       |
| -------------------- | ---------------------------------------- | ---------------------------------------------------- | -------------- |
| **横向（同层解耦）** | 同一个层内，业务和业务之间如何不互相纠缠 | 先分出要做哪些事 → 把事切成模块 → **高内聚低耦合**   | §2.1（D 系列） |
| **纵向（跨层分层）** | 层与层之间如何组织、依赖如何单向         | 某个模块/业务复杂到一定程度 → **重新抽象出一个新层** | §3 分层约束    |

**递归演进（两个方向的关系）**：

```
先分模块（横向）→ 某个模块变复杂 → 分层（纵向）→ 新层内再分模块（横向）→ 再复杂再分层（纵向）→ …
```

- 复杂度是 **递归涌现**的，不是一开始就能规划完——这正是「动态分层」「最小建模起步」等"按需演进"原则的根本原因
- 两个方向缺一不可：只分层不拆模块 → 层内大泥球；只拆模块不分层 → 平面铺开无法承载深度

**横向维度的实现：高内聚、低耦合**（模块设计，具体规则见下方 D 系列）：

| #   | 规范                                                                                                                                                                                                                                                                                | 检查方式                                                                      |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| D1  | **深模块**：接口简单程度必须显著低于实现复杂程度；浅模块（接口≈实现）须给出理由或直接内联                                                                                                                                                                                           | 检查：方法数≤5（ast-grep 扫方法数）且圈复杂度>10即审（npx complexity-report） |
| D2  | **信息隐藏**：每个模块封装设计决策；同一知识出现在多个模块 = 信息泄露，必须合并或提取封装                                                                                                                                                                                           | 审查：同一常量/格式/决策是否在多处出现                                        |
| D3  | **按知识域拆，不按时间顺序拆**：类的边界 = 知识边界，不是流程步骤——不得按"读→解析→存"这类执行时序拆类（同一知识被切碎到多个类 = 信息泄露），把共享同一知识的所有逻辑收进一个类                                                                                                      | 审查：类名是否暗示执行步骤（读取/解析/预处理）/ 改一处规则是否要改多个类      |
| D4  | **通用与专用分离**：通用机制内不得混入专用代码（专用逻辑放使用方）；接口满足当前需求但可复用                                                                                                                                                                                        | 审查：工具类是否内嵌单一用途逻辑                                              |
| D5  | **禁止浅模块**：禁止透传方法（只转发不做事）、禁止"为小而小"的拆分（多类症）、禁止仅单调用点的薄方法——浅模块应内联或加功能变深                                                                                                                                                      | 审查：方法是否只是转发 / 类是否只有单一调用者                                 |
| D6  | **禁止透传变量**：新参数不得贯穿多层签名传递；全局状态统一收敛到 Context 对象                                                                                                                                                                                                       | 审查：参数是否连续多层同名传递                                                |
| D7  | **接口简单 > 实现简单**：把不可避免的复杂性下沉到模块内部；新增配置项需在 ADR 记录调用方无法定优值的理由，否则内部自动处理                                                                                                                                                          | 检查：新增配置项是否在 ADR 记录理由                                           |
| D8  | **开闭原则（OCP）**：对扩展开放、对修改关闭——新需求通过新增（实现/扩展/策略）满足，不修改已有逻辑                                                                                                                                                                                   | 审查：新增需求是否改动已有代码                                                |
| D9  | **接口隔离（ISP）**：客户端不应依赖它不使用的能力——接口按调用方需求拆分，避免"大而全"                                                                                                                                                                                               | 审查：接口是否有用不到的成员                                                  |
| D10 | **接口与多态（何时用接口）**：用接口**减少依赖**（调用方定义接口，被调用方依赖调用方——控制反转），但**不在聚合/值对象内部滥用**——接口只在**层边界**（domain/infra 分界）与**上下文边界**（跨上下文 contract）使用；同一聚合/值对象内部直接调，不为每个方法建接口（避免类/方法爆炸） | 审查：接口是否在边界层（domain/contract）/ 是否在聚合内部滥用接口             |
| D11 | **读写分离（目的）**：**读尽可能简单**——直接读存储层数据，只做无业务意义的字段转换；**写必须走聚合入口**——通过聚合根方法写入，保证业务规则。读走值对象/DTO，写走聚合                                                                                                                | 审查：读是否绕开聚合直接查存储 / 写是否通过聚合根                             |

> 纵向维度的实现（分层约束）见 STRUCTURE §3.1 代码分层细则。

### 2.2 单一事实源（SSOT）

> 手段：为实现「降低复杂度」而消除信息重复与漂移（A 消除模糊性）。
>
> **单一事实源不是只指文档**——它覆盖项目里所有信息载体（代码 / 注释 / 文档）之间的 **冲突裁决标准**：

| 信息载体之间 | 冲突时以谁为准                                                     |
| ------------ | ------------------------------------------------------------------ |
| 代码 与 代码 | 以运行正确且最新合入的代码为准（Git 历史裁定）                     |
| 代码 与 注释 | **以代码为准**——注释必须反映代码，注释与代码不符即注释过时，改注释 |
| 代码 与 文档 | **以代码为准**——文档必须反映代码，文档与代码不符即文档过时，改文档 |
| 注释 与 注释 | 以代码为准 + 就近原则（离代码越近的注释越可信）                    |
| 文档 与 文档 | 以代码为准 + SSOT（同一信息只在一个文档维护，重复处引用不复制）    |

**核心原则：代码是唯一事实（Code is the Source of Truth）**——文档和注释是代码的投影（不是独立真相），与代码冲突时改文档/注释而非代码；代码本身之间的冲突由
Git 裁决。

| #    | 规范                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | 检查方式                                                                                  |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| S1   | **代码是唯一事实**：文档和注释必须反映代码；任何载体与代码冲突时，改文档/注释而非代码                                                                                                                                                                                                                                                                                                                                                                                | 审查：文档/注释是否与代码矛盾                                                             |
| S2   | **同一信息只在一个文档维护**：其他文档引用不复制（复制必然漂移）；发现重复 → 归并到唯一源，其余改为引用                                                                                                                                                                                                                                                                                                                                                              | 审查：同一信息是否在多处重复书写                                                          |
| S2.1 | **文档间引用单向向下 + 精简提及**：文档间的**可点击导航链接只允许上层 → 下层**（L0/L1 可链 L2/L3/L4，下层不链回上层）。下层引用上层内容时**只做精简文字提及**（如「SSOT」「见宪法」），不写上层文档的路径/章节锚点——**宪法（L0）全局加载**（跨任务/跨 Agent 上下文恒有），读者无需跳转即可理解；业务内容 SSOT 在上层，下层引用不复制。同级（同层）文档间引用属协作，允许                                                                                             | 审查：下层文档是否出现 `docs/L0/…` 或「CONSTITUTION §x」类精确锚点；导航链接是否下层→上层 |
| S3   | **注释就近原则**：注释描述它旁边的代码；离代码越远的信息越容易过时，关键注释必须紧贴代码                                                                                                                                                                                                                                                                                                                                                                             | 审查：注释与代码的距离是否过大                                                            |
| S4   | **差异主动修复**：执行任何操作（读取/变更）时发现文档/注释与代码有差异 → **主动修复文档/注释**（即使与本次功能无关，无需用户授权——不影响运行）                                                                                                                                                                                                                                                                                                                       | 检查：发现差异即修，不积压                                                                |
| S5   | **差异分诊（对齐机制，即业界 Bug Triage）**：文档/注释与代码有差异时，按「自动化优先 → 默认以代码为准 → 漂移定级 → Bug 例外」四步分诊（流程见下方）                                                                                                                                                                                                                                                                                                                  | 审查：差异归属判断（bug vs 漂移）+ 是否用户介入 + 自动化是否可用                          |
| S6   | **文档/注释当前态**：永远表现**当前设计意图**（G），不写因果链（不记录"以前是什么/为什么改"）；更新只写预期值；历史/原因归 ADR（决策原因）/ git log（文档文件演进），正文仅留当前意图G。注：RESEARCH / deep-dives 的**技术论证过程**（候选/对比/POC/来源附录）属当前意图G保留；仅**文档演进历史**（合并/改名/编号沿用/旧路径）属因果链，移至 git log / ADR，正文不写                                                                                                 | 审查：文档/注释是否含过时历史信息                                                         |
| S6.1 | **删除/迁移章节规范**（S6 的执行细则）：① 删除/迁移章节 → **删净并重编号连续**，**禁止留「已迁移/已删除至 X」因果链占位**（如 `## 4. 数据设计（已迁移至 DATA-ARCHITECTURE）`——违反 S6 当前态）；② 若需保留导航 → 用**不渲染的 HTML 注释**（`<!-- 内容已迁移至 DATA-ARCHITECTURE -->`）而非正文说明；③ 迁移/删除后 → `grep -rn "§x" docs/ .omo/rules/` **批量替换所有下游引用并验证零残留**——引用检查是**必须步骤**，非可选；④ 完成判定加「全仓无指向已删章节的引用」 | 审查：删章/迁移后是否有「已迁移」正文占位；grep 是否残留指向已删章节的 §x 引用            |
| S7   | **文档与代码同交付（底线）**：任何实质代码变更（新增功能/修改逻辑/架构调整），会话结束前必须同步文档——文档不是可选项，是交付物的一部分                                                                                                                                                                                                                                                                                                                               | 审查：代码变更是否漏同步文档                                                              |
| S8   | **漂移清单跟踪（.omo/drift/ · 按文件一清单 · 固定格式可解析）**：发现 code-doc 漂移时，**按漂移文件**各落一清单 `.omo/drift/<doc>.md`（如 `DOMAIN-MODEL.md`→`.omo/drift/DOMAIN-MODEL.md`，`docs/L2/FOO.md`→`.omo/drift/FOO.md`；与 `.omo/plans` 同级，过程态不提交）；**默认记录不问处置**（发现即记，不填以文档/以代码）；表头固定 `                                                                                                                                | #                                                                                         | 位置 | 差异（文档 vs 代码） | 状态 | `（`状态`枚举 `待修复/修复中/已修复/已验证`，符号 `☐/◐/☑`可选前缀）；真正要解决时必问 Gap 处置（1 以文档为准 / 2 以代码为准 / 3 逐条判断），选 3 时补 `建议`/`判定`列（建议=AI 按 S5 预判 1/2，判定=用户逐条 1/2）并逐条更新；每修一条立即更新状态；单文件全部`已验证`后立即 `rm` 该 drift 文件（空目录一并删除），禁止入库 | 审查：是否按文件一清单；默认记录是否无处置列；完成后是否已删除对应 drift 文件 |

**差异分诊流程（S5 执行细则）**：执行序：①→④判定→②→③

```
发现 代码/注释/文档 有差异
  → 先判是否为 Bug（④）；非 Bug 才走②③
  ├─ ① 自动化优先：能由工具自动生成/校验的对齐（如从代码生成文档、链接/示例校验）
  │     → 直接自动化，不走分诊（无自动化工具时跳过此步）
  ├─ ② 默认以代码为准：AI 自主修复文档/注释去匹配代码
  │     （不写死"先改代码还是先改文档"的先后；文档改错代价低可放心对齐；目标让三者离散度收敛）
  ├─ ③ 漂移定级：影响 API 契约/用户故事验收即严重，否则轻微；严重优先修，轻微（措辞/表述）顺手修
  └─ ④ 唯一例外 = Bug：代码实现偏离文档真实意图（文档真实反映用户需求，代码写错）
        → 必须用户介入判断（Bug Triage 的"确认"环节）
        → 用户认可才修代码（文档整体意思不变，可微调）；用户不认可则按文档为准修文档
```

## 3. 文档架构（L0-L4 + common 层）

### 3.1 文档架构表

> **本节 = 文档目录规范的 SSOT**（文档体系怎么分层、每层放什么类型的文档）。 **项目目录树（全项目文件组织）在 STRUCTURE**
> ——docs/ 子树的目录名遵守本节分层，但 STRUCTURE 不重复本节规则。
>
> 依赖方向：L0 → L1 → L2 → L3 → L4 单向向下；common 层贯穿所有层（不归属任何层，服务全局）。上层变更须沿链传播。
>
> 文档架构基于 **TOGAF 方法论**组织——每层/每文档对应一个架构视角（业务/数据/应用/技术/迁移/契约/质量），每份文档聚焦单一视角，职责互不重叠。
>
> **文档体系结构以本表为准**（L0-L4 + common 分层、必选性、更新条件）——不再单独画图，表格即 SSOT。各文档的目录命名（kebab-case
> 等）、判定细则、SSOT 分工由对应 rule 与 STRUCTURE 目录树承载，本节表格只标定位、更新条件与必选性。
